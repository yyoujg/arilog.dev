> 관련 프로젝트: [blogsumnail](/projects/blogsumnail)
> 읽은 글: [[번역] 취향과 판단력을 얻는 법](https://www.yeongseo-blog.site/blog/earning-taste-and-judgment) (Addy Osmani [원문](https://addyosmani.com/blog/earning-judgment/), 윤영서 번역)

판단력은 어디서 오는가에 대한 글이다. 읽고 나서 blogsumnail 커밋 로그를 다시 열었다.
내가 판단력이라고 부를 만한 게 쌓인 자리는 잘 만든 코드보다, 틀렸다는 걸 확인하고
고친 커밋 쪽에 더 많았다.

## 아티클 요약: 저절로 쌓이던 판단력이 더는 저절로 쌓이지 않는다

예전에는 반복 작업을 하다 보면 무엇이 좋은지, 무엇이 위험한지에 대한 감각이 부산물로
생겼다. 저자는 그 반복이 줄어든 지금은 판단력을 일부러 길러야 한다고 본다.

AI 출력을 감독하는 역할이 그 대안이 될 수 있느냐에 대해서는 회의적이다. 저자가 인용한
Shaw와 Nave의 연구(참가자 1,372명)에서는 사람들이 틀린 AI 출력을 약 80% 받아들였고,
정확도는 약 15%p 떨어졌는데 자신감은 약 12% 올랐다. 틀린 답을 고르면서 더 확신하게 된 셈이다.

처방은 구체적이다. 틀린 판단을 한 문장씩 기록해 두고 30일 뒤에 다시 읽어 패턴을 찾는다.
그리고 무엇을 만들지 정하는 일(명세)과 그게 맞는지 확인하는 일(검증)을 분리한다.

## 내 사례 두 건

blogsumnail은 네이버 블로그 썸네일과 스킨을 브라우저에서 만드는 도구다. 아래 두 건은
모두 "그럴 것이다"로 코드나 문장을 썼다가 실측으로 뒤집은 경우다.

### 1. 네이버가 스킨을 3000px로 늘려 줄 거라고 믿었다

스킨메이커는 배경 PNG를 내보낸다. 네이버 스킨 배경은 최대 3000px까지 올릴 수 있어서,
네이버가 이 이미지를 3000px 폭으로 확대해 보여준다고 생각했다. 그러면 작은 캔버스에서
만든 배경은 확대될 때 글씨가 뭉개지니, 내보낼 때부터 키워 두자는 판단이었다.

2026-06-30에 들어간 `67437fc`의 커밋 제목이 그 전제를 그대로 담고 있다. "스킨 내보내기
항상 가로 3000px 보장 - 작은 캔버스에서도 네이버 w3000 확대 시 글씨 선명". 코드는 이랬다
(`components/SkinMakerTool.tsx` 490행, 해당 커밋 기준).

```ts
// 항상 가로 ~3000px로 내보내 네이버 스킨배경(w3000)에서 글씨가 선명하게.
const exportScale = Math.min(4, Math.max(1, 3000 / cw));
```

같은 날 `78df2c1`은 상한을 2배로 두고 있었고, 07-02의 `23ae46a`에서는 상한 없이
`Math.max(1, 3000 / cw)`가 됐다. 배율 공식은 세 번 바뀌었지만 "네이버가 확대한다"는
전제는 한 번도 의심받지 않았다.

2026-08-27 `07964be`에서 이 전제가 뒤집혔다(같은 파일 1156행, 해당 커밋 기준).

```ts
// 네이버는 스킨배경을 원본 크기 그대로(가운데 정렬·가로 반복) 표시한다 - 실측 확인.
// 확대해 내보내면 배경에 그린 메뉴 칸이 함께 커지는데 실제 위젯 격자는 170px·간격 10px로
// 고정이라, cw=1920을 3000으로 확대하면 5칸 끝단이 400px 넘게 어긋난다. 항상 1:1로 낸다.
const exportScale = 1;
```

네이버는 확대하지 않았다. 원본 크기 그대로 가운데 정렬하고 가로로 반복한다. 배경에 그린
메뉴 칸은 배율만큼 커지는데 실제 위젯 격자는 170px 칸, 10px 간격으로 고정이라, 확대할수록
그림과 클릭 영역이 벌어졌다. 선명하게 하려던 배율이 위치를 깨고 있었다. 주석에 "실측
확인"이라고 적혀 있지만, 어떤 화면에서 어떻게 확인했는지는 커밋에 남기지 않았다.

그리고 정정은 문서까지 가지 못했다. 지금 README 44행은 여전히 이렇게 적혀 있다.

> 스킨 PNG는 `exportScale = max(1, 3000 / cw)`로 캔버스를 확대해, 네이버가 스킨을 3000px로 늘려 표시해도 선명하게 유지

코드는 08-27에 고쳐졌고, README는 그 전 공식과 그 전 전제를 설명하고 있다.

### 2. "고화질 옵션을 켜면 실제 800px급"이라고 썼다

썸네일 크기 안내 글(`data/blogPosts.ts`)에 "고화질 옵션을 켜면 실제 800px급으로
저장됩니다"라는 문장이 있었다. 이 숫자를 잰 기록은 없었다.

2026-10-06 `af3e25e`에서 캡처 스크립트(`scripts/capture-tool-shots.ts`)에
`--measure-download` 모드를 넣었다. Playwright로 실제 다운로드 버튼을 눌러 PNG를 받고,
파일의 IHDR 청크(16~24바이트)에서 가로·세로를 읽는다. 화면에 보이는 미리보기 크기도 함께
찍는다.

| 화면         | 옵션        | 저장된 PNG |
| ------------ | ----------- | ---------- |
| PC           | 고화질 (2x) | 1000x1000  |
| PC           | 표준 (1x)   | 500x500    |
| 390px 모바일 | 고화질 (2x) | 648x648    |

저장 크기는 고정값이 아니라 미리보기 크기를 따랐다. PC에서 고화질은 800px급보다 크고,
표준은 그보다 작고, 모바일 고화질은 648px이다. 같은 날 `3f8ee19`에서 문장을 이 값으로 고쳤다.

### 이미 한 번 해 본 정정

이 블로그의 [size-limit 글](/blog/posts/size-limit-bundle-measurement-gap)도 발행 후에
원인 서술을 고쳤다. 처음에는 "진입점 파일만 측정"이 원인이라고 썼는데, 설정 히스토리를
다시 보니 틀렸고, 실제 원인은 다중 entry 빌드에서 컴포넌트 파일이 스텁이 된 것이었다.

## 정정 기록 표

| 처음 믿은 것                         | 확인 방법                               | 실제                                       | 남은 흔적                                  |
| ------------------------------------ | --------------------------------------- | ------------------------------------------ | ------------------------------------------ |
| 네이버가 스킨 배경을 3000px로 확대   | 네이버 표시 확인 (방법은 커밋에 미기록) | 원본 크기 그대로 가운데 정렬, 가로 반복    | `67437fc` 커밋 제목, README 44행의 옛 공식 |
| 고화질 저장은 800px급                | Playwright 다운로드 PNG의 IHDR 읽기     | 미리보기 크기를 따라 1000 / 500 / 648px    | 측정 모드가 스크립트에 남음 (`af3e25e`)    |
| size-limit 결함 원인은 진입점만 측정 | size-limit 설정 히스토리 재확인         | 다중 entry 빌드에서 컴포넌트 파일이 스텁화 | 글 상단 정정 블록                          |

세 건 모두 처음 믿은 것은 그럴듯했다. 3000px 한도가 있으니 확대할 것 같았고, 권장 크기가
800px이니 고화질이면 그쯤일 것 같았다. 틀린 이유는 확인하지 않았다는 것 하나였다.

## 다른 점과 한계

아티클은 의식적으로 오답 노트를 쓰고 30일 뒤에 패턴을 보라고 한다. 나는 그런 노트를 따로
쓰지 않았다. 위 표는 오늘 커밋 로그에서 거꾸로 모은 것이고, 커밋 메시지와 코드 주석이
우연히 오답 노트 역할을 해 준 셈이다. 우연에 기댄 기록이라 빈 곳이 있다. 1번은 무엇을
어떻게 실측했는지 남기지 않았고, 2번은 처음 800px급이라는 숫자가 어디서 나왔는지 기록이 없다.

명세와 검증의 분리도 절반만 했다. 2번은 측정 스크립트를 따로 만들어 검증을 코드로 남겼다.
1번은 확인은 했지만 다시 돌릴 수 있는 형태로 남기지 않았고, 그래서 README처럼 같은 전제를
설명하는 다른 문서까지 따라가 고치지 못했다.

## 배운 점

- 판단력이 쌓인 자리는 "틀렸다"를 실측으로 확인한 커밋이었다. 확인 방법까지 남겨야 다음에 같은 전제를 다시 의심할 수 있다.
- 정정은 코드에서 끝나지 않는다. 같은 전제를 설명하는 README, 안내 문구, 커밋 제목을 grep으로 같이 찾는다.
- 숫자를 문장에 쓰기 전에 그 숫자를 만든 측정이 있는지 본다. 없으면 측정을 먼저 만든다.
