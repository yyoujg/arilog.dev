> 읽은 글: [How Turbopack chunks your JavaScript](https://nextjs.org/blog/turbopack-chunking) (Next.js 블로그, 2026-09-03)

JavaScript Weekly 801호 헤드라인으로 Turbopack 청크 분할 글이 왔다. 부제가
"8개 청크가 355개보다 무거울 수 있다"였다. 읽다 보니 몇 달 전에 고친 size-limit
게이트 결함이 같은 문제의 반대편이었다는 걸 알게 됐다.

## 아티클 요약: 요청 수와 코드량은 서로 싸운다

번들러가 코드를 청크로 나누는 방식은 크게 세 가지로 생각할 수 있다.

| 전략                  | 장점                              | 단점                                           |
| --------------------- | --------------------------------- | ---------------------------------------------- |
| 앱 전체를 청크 하나로 | 두 번째 페이지부터 전부 캐시 히트 | 가벼운 페이지도 전체 JS를 받는다               |
| 페이지당 청크 하나    | 과다 전송 없음                    | 공용 컴포넌트가 페이지마다 중복 다운로드       |
| 모듈당 청크 하나      | 과다 전송도 중복도 없음           | 요청이 수백 개, 작은 파일은 압축 효율도 나쁘다 |

Turbopack은 그 사이에서 작은 청크를 병합한다. 병합 후보는 같은 **chunk group**
(한 페이지가 함께 로드하는 청크 묶음) 안에서만 고른다. 같은 그룹은 어차피 같이
받으니 병합해도 과다 전송이 생기지 않는다. 대신 다른 페이지로 이동할 때 병합된
파일을 재사용하지 못하면 같은 코드를 두 번 받게 된다. 그래서 "한 페이지 보고 나가는
세션"과 "다른 페이지로 이동하는 세션"의 비율(기본 가정 2:1)로 병합의 득실을 가중한다.

가장 인상적인 건 측정 방식이었다. 파일 하나의 크기가 아니라, nextjs.org에서 같은
8단계 내비게이션을 세 가지 설정으로 돌려 **세션 전체의 요청 수와 다운로드량**을 비교했다.

| 설정             | 전체 다운로드 | 전체 요청 |
| ---------------- | ------------- | --------- |
| 병합 안 함       | 561.6 KiB     | 96        |
| Turbopack 기본값 | 554.8 KiB     | 38        |
| 그룹당 청크 하나 | 610.0 KiB     | 15        |

최대 병합은 첫 로드에서 가장 유리했지만 이동이 이어지자 코드를 10% 더 받았다.
어느 설정이 낫냐는 질문은 "어떤 이동 시나리오에서"를 붙여야 답이 나온다.

Next.js 16.3에는 이 한계를 줄이는 실험 옵션이 들어갔다. 병합 청크와 함께 병합 전
조각을 같이 내보내 런타임이 이미 캐시된 것을 보고 고르게 하는 옵션, 실제 방문 패턴
(첫 로드 비중, 우선 라우트, 함께 방문되는 라우트 묶음)을 설정으로 알려주는 옵션 등이다.

## 내 사례: 청크 분할이 만든 136 B짜리 숫자

디자인 시스템 번들은 tsup 다중 entry로 빌드했다. 공용 코드가 별도 청크로 빠지면서
`dist/components/Button/Button.js` 같은 컴포넌트 파일은 공용 청크를 `import`해서
다시 내보내기만 하는 스텁이 됐다. size-limit 게이트는 그 스텁 하나를 쟀다.

|                 | 게이트가 잰 것 | 소비자가 실제로 받는 것                 |
| --------------- | -------------- | --------------------------------------- |
| 대상            | 스텁 파일 하나 | 스텁 + 의존 청크 + CSS, 트리셰이킹 결과 |
| Button (brotli) | 136 B          | 8,970 B                                 |

청크 분할은 잘 동작하고 있었다. 공용 코드를 한 번만 받게 만드는, 아티클이 말하는
바로 그 최적화다. 문제는 분할된 결과물의 파일 하나를 "컴포넌트 크기"로 읽은 쪽에
있었다. 수정 내용은 [기존 글](/blog/posts/size-limit-bundle-measurement-gap)에
정리했다. 측정 방식을 `preset-small-lib`로 바꿔 소비자 import 결과를 brotli 기준으로 재게 했다.

## 두 글이 가리키는 같은 지점

|                       | Turbopack 아티클                 | 내 size-limit 게이트                |
| --------------------- | -------------------------------- | ----------------------------------- |
| 잘못 재기 쉬운 단위   | 청크 파일 하나의 크기            | 컴포넌트 파일 하나의 크기           |
| 실제로 재야 하는 단위 | 이동 세션 전체의 요청 수와 KiB   | 소비자 import 시 번들되는 최종 크기 |
| 청크 전략이 바뀌면    | 파일 수와 크기가 통째로 달라진다 | 스텁이 되어 숫자가 사실상 0이 된다  |

청크 전략은 파일 하나의 크기가 뭘 뜻하는지를 바꿔 버린다. 분할을 세게 하면
파일은 작아지고 개수는 늘어난다. 병합을 세게 하면 반대다. 어느 쪽이든 파일 하나만
보면 착시가 생긴다. 그래서 측정 단위는 파일이 아니라 사용자(앱이라면 방문자, 라이브러리라면
소비 앱)가 실제로 받는 것이어야 한다.

## 다른 점도 있다

라이브러리 번들러와 앱 번들러의 목적은 다르다. tsup으로 라이브러리를 만들 때 청크
분할은 최종 사용자를 위한 최적화라기보다, 소비 앱의 번들러가 트리셰이킹하고 다시 묶을
재료를 내놓는 일에 가깝다. 실제 네트워크 요청을 결정하는 건 소비 앱 쪽 번들러다.
그래서 라이브러리 게이트는 "소비자 import 결과의 크기"까지만 책임지고, 요청 수나 캐시
재사용 같은 판단은 아티클처럼 앱에서 시나리오를 정해 실측해야 한다. 이 경계를 섞으면
라이브러리 쪽에서 앱의 일을 추측하게 된다.

## 배운 점

- 번들 숫자를 볼 때는 먼저 "이 숫자는 어떤 청크 전략의 결과물을 쟀나"를 확인한다.
- 측정 단위는 사용자가 실제로 받는 단위로 맞춘다. 앱은 이동 세션, 라이브러리는 소비자 import 결과다.
- 비교할 때는 같은 시나리오를 고정하고 설정만 바꾼다. 아티클의 8단계 내비게이션 표가 좋은 본보기였다.
