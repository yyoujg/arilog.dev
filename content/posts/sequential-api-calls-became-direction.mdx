> 관련 프로젝트: [CRS 어드민 상품마감·요금재고 화면 재설계](/projects/crs-admin-inventory-redesign)

같은 화면을 2024년에 한 번 설계하고, 2025년에 다시 설계했다. 다시 손댄 이유는 기능이 부족해서가 아니라, **호출 순서 자체가 사용자가 못 바꾸는 제약**이 돼 있었기 때문이다.

## 문제 — 순서가 곧 방향이 됐다

상품마감·요금재고 화면은 3개 API를 순차로 호출하는 구조였다. 문제는 이 "순차"가 단순한 로딩 단계가 아니라, **호출 순서 자체가 조회 방향을 결정**하고 있었다는 것이다.

첫 API가 응답하면 그 결과의 첫 값이 자동으로 선택된다. 그 선택값을 기준으로 다음 API가 호출된다. 이 과정이 반복되면서, 사용자가 원래 보고 싶었던 조회 방향과 무관하게 **첫 단계의 자동 선택이 이후 단계 전체를 가둬버렸다.** "반대 방향으로 훑어보고 싶다"는 요구가 있어도, 구조 자체가 한쪽 방향만 허용했다.

## 접근 — 고정된 순서를 없애고 서로를 필터로 받는다

해법은 API를 더 최적화하는 게 아니라, **순서가 한쪽으로 고정된 구조 자체를 없애는 것**이었다. 호텔·객실·패키지를 각각 다른 API로 부르던 것을 검색 엔드포인트 `/api/product/search` 하나로 합치고, `type: 'hotel' | 'room' | 'package'`로 무엇을 찾는지 고르게 했다. 그리고 객실 검색은 패키지 ID를, 패키지 검색은 객실 ID를 선택적으로 받게 해서 **어느 쪽을 먼저 골라도 다른 쪽을 좁힐 수 있게** 했다.

```ts
// 실제 요청 형태 (요약)
getHotelList(); // { type: 'hotel' }
getRoomList({ hotelId, pkgId }); // { type: 'room', hotelId, pkgId? }
getPackageList({ hotelId, roomId }); // { type: 'package', hotelId, roomId? }
```

프론트의 호출 수는 그대로 3개다. 호텔·객실·패키지 목록은 여전히 각자의 쿼리로 부른다. 바뀐 건 호출 개수가 아니라, 첫 응답의 첫 값을 자동으로 골라 다음 단계에 넘기던 연결을 끊었다는 점이다. 이전에는 "호텔 -> 객실 -> 패키지" 순서로만 좁힐 수 있었는데, 이제는 객실을 먼저 고르든 패키지를 먼저 고르든 사용자가 고른 값이 다른 목록의 필터가 된다. `direction` 같은 파라미터가 생긴 게 아니라, 교차 필터로 순서 제약을 없앤 것이다.

## 정리

| 구분           | before(순차 호출)             | after(통합 검색 + 교차 필터)               |
| -------------- | ----------------------------- | ------------------------------------------ |
| 엔드포인트     | 호텔·객실·패키지 각각         | `/api/product/search` 하나 + `type`        |
| 조회 순서      | 호텔 -> 객실 -> 패키지로 고정 | 객실·패키지가 서로를 필터로 받아 순서 무관 |
| 다음 단계 입력 | 이전 단계의 자동 선택값       | 사용자가 고른 값                           |
| 프론트 호출 수 | 3개                           | 3개 (그대로)                               |

같은 화면을 두 번 설계하게 된 이유는 처음 설계가 "동작은 하지만 방향이 갇혀 있는" 구조였기 때문이다. 호출 수는 그대로 두고도 제약은 풀 수 있었다. **API를 몇 개 쓰느냐보다, 그 호출 순서가 사용자가 통제할 수 없는 제약으로 굳어지지 않았는지가 먼저 물어야 할 질문**이었다.
