화면 하나가 뜰 때 API를 다섯 개쯤 동시에 부르는 건 흔하다. 문제는 **그 다섯 개가 하필 토큰 만료 경계에서 동시에 나갈 때** 생긴다. 다섯 개가 **전부 동시에 401**을 받는다.

## 문제 — 동시 401이 리프레시 레이스를 만든다

액세스 토큰이 만료된 직후, 병렬로 나간 요청들은 각자 401을 받는다. 여기까진 정상이다. 문제는 **그다음**이다.

각 요청이 "401 받았으니 토큰을 갱신하고 재시도하자"라고 **각자 리프레시를 호출**하면:

- **리프레시가 여러 번 중복 실행**된다. (요청 수만큼)
- 리프레시 API가 회전(rotation) 방식이면, **먼저 갱신된 토큰을 나중 리프레시가 무효화**한다.
- 그 결과 어떤 요청은 이미 무효가 된 토큰으로 재시도해 다시 깨지고, **로그아웃이 튀거나** 화면이 반쯤 실패한 상태가 된다.

즉 "토큰 만료"라는 정상 상황이, **동시성 때문에 로그아웃 사고**로 번질 수 있는 구조였다. 실제 사고 기록은 남아 있지 않고, 팀에서 큐로 바꾼 커밋에도 증상은 적혀 있지 않다.

## 처음 넣은 구조 - 요청마다 각자 리프레시

2024년 3월 12일, 401을 받으면 리프레시 토큰으로 갱신하고 원래 요청을 다시 보내는 응답 인터셉터를 내가 처음 넣었고, 19일까지 몇 차례 고쳤다. 요청마다 `_retry` 플래그를 세워 같은 요청이 두 번 갱신을 부르지는 않게 했지만, **401을 받은 요청 각각이 자기 리프레시를 호출**하는 구조였다. 요청이 하나씩 나갈 때는 문제가 없다. 동시에 여러 개가 401을 받는 순간에는 위에서 적은 중복 리프레시가 그대로 생긴다.

| 안  | 방식                                                           | 문제                                                                                      |
| --- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| A   | 401마다 각자 리프레시 (내가 처음 넣은 구조)                    | 동시 401이면 리프레시가 요청 수만큼 실행된다                                              |
| C   | 응답 인터셉터에서 리프레시를 **1회로 직렬화 + 대기 요청 큐잉** | 첫 401만 리프레시하고, 그 사이 들어온 401들은 큐에서 기다렸다 새 토큰으로 **일괄 재시도** |

## 팀에서 바꾼 구조 - "리프레시는 한 번만, 나머지는 기다렸다 재시도"

2주 뒤인 4월 1일, 동료가 이 인터셉터를 큐 방식(C)으로 바꿨다. 같은 날 다른 axios 인스턴스에도 같은 구조가 들어갔다. 내가 한 건 그 전 단계(A)였고, 큐는 내 작업이 아니다. 이 글은 두 구조를 나란히 놓고 무엇이 달라졌는지 읽어 본 기록이다.

핵심 문장은 이거다.

> **첫 번째 401만 리프레시를 실행하고, 그 사이 들어온 나머지 401들은 큐에 넣고 기다렸다가, 갱신이 끝나면 새 토큰으로 한꺼번에 재시도한다.**

실제 코드는 모듈 변수 두 개로 이 일을 한다. 리프레시가 진행 중인지를 나타내는 `isRefreshing`, 그리고 기다리는 요청의 콜백을 쌓아 두는 `refreshSubscribers` 배열이다. 진행 중이면 새로 들어온 401 요청은 리프레시를 또 부르지 않고 콜백을 배열에 넣은 채 기다리고, 갱신이 끝나면 배열을 돌며 새 토큰으로 원래 요청을 다시 보낸다. 이른바 **single-flight**(같은 작업은 동시에 한 번만) 패턴이다.

```
// 구조 요약 (실제 코드를 줄인 것)
let isRefreshing = false;
let refreshSubscribers = [];

onResponseError(원요청, error):
  if (error.status !== 401 || 원요청._retry) throw error
  if (!isRefreshing):
    원요청._retry = true; isRefreshing = true
    try:
      token = await refresh()
      refreshSubscribers.forEach(cb => cb(token)); refreshSubscribers = []
      return retry(원요청, token)
    catch: handleTokenRefreshError(); throw          // 첫 요청만 reject
    finally: isRefreshing = false
  else:
    return new Promise(resolve =>                     // reject 경로가 없다
      refreshSubscribers.push(token => resolve(retry(원요청, token))))
```

다섯 개의 401이 들어와도 리프레시는 한 번만 나가고, 나머지 넷은 콜백으로 그 결과를 기다린다.

## 읽어 보니 남아 있던 빈틈

큐 코드를 다시 읽으면서 "실패하면 대기 요청을 전부 정리하고, 재시도는 한 번으로 막는다"고 생각했던 부분이 실제로는 그렇지 않다는 걸 확인했다.

- **리프레시가 실패하면 reject되는 건 첫 요청 하나뿐이다.** 대기 중인 요청은 resolve 콜백만 등록돼 있고 reject 경로가 없어서, Promise가 끝나지 않은 채 남는다. 실제 정리는 `handleTokenRefreshError`가 알림을 띄우고 로그인 화면으로 페이지를 이동시키는 것으로 이뤄진다. 페이지가 바뀌니 눈에 띄는 문제는 없지만, 대기 요청을 명시적으로 끝내는 코드는 아니다.
- **`_retry` 플래그는 첫 요청에만 선다.** 대기했다가 재시도한 요청은 플래그가 없어서, 그 재시도가 또 401을 받으면 다시 인터셉터를 탄다. "재시도 1회 제한"은 첫 요청에만 해당한다.

## 정리

| 지표                      | A(각자 리프레시, 2024-03) | C(인터셉터 큐, 2024-04-01)                         |
| ------------------------- | ------------------------- | -------------------------------------------------- |
| 동시 401 시 리프레시 횟수 | 요청 수만큼(N번)          | **1번**                                            |
| 리프레시 실패 시          | 요청마다 각자 실패 처리   | 첫 요청만 reject, 대기 요청은 페이지 이동으로 정리 |
| 재시도 제한               | 요청마다 `_retry`         | 첫 요청에만 `_retry`                               |

돌아보면 이건 "인증" 문제라기보다 **동시성** 문제였다. 토큰 만료 자체는 정상 흐름이고, 문제는 **여러 요청이 같은 일(리프레시)을 동시에 하려던 것**이었다. 내가 처음 넣은 구조는 요청 하나 단위로만 생각했고, 동시에 들어오는 경우를 팀의 수정을 보고서야 구분하게 됐다. 그리고 큐를 넣었다고 실패 경로까지 정리되는 건 아니라는 것도 코드를 다시 읽으며 알았다. single-flight를 쓸 때는 성공 경로만큼 **대기 중인 쪽을 어떻게 끝낼지**를 같이 봐야 한다.
