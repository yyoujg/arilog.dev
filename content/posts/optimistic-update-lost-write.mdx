겹치는 인터랙션에서 낙관적 쓰기를 어떻게 맞추는지에 대한 글을 읽었다. 읽으면서 너구리
게임에서 고친 버그 세 건이 떠올랐다. 셋 다 요청은 성공했고, 앞서 저장된 값만 사라져 있었다.

## 아티클 요약: 다음 상태는 마지막 저장 결과 위에서 계산한다

사용자가 빠르게 여러 번 누르면 쓰기가 겹친다. Next.js는 서버 액션을 하나씩 순서대로
처리하지만, 순서가 보장된다고 끝나는 게 아니다. 큐에 넣기 전에 클라이언트가 "다음 상태"를
미리 계산해서 보내면, 앞 요청이 끝나기 전의 값을 기준으로 계산한 셈이라 앞선 변경이 덮인다.

저자의 처방은 이렇다.

- `useActionState`로 이전 액션의 결과를 다음 액션의 입력으로 넘긴다. 그러면 각 쓰기가 마지막으로 저장된 결과 위에 쌓인다.
- 실패 시 롤백은 "반대 방향 변경"을 다시 계산하지 않고, 저장돼 있던 이전 상태를 그대로 돌려준다.
- 폴링처럼 데이터가 사용자 조작 없이 스스로 바뀌는 경우에만 SWR이나 TanStack Query 같은 클라이언트 캐시를 쓴다.

결론은 데이터의 주인은 서버이고, 클라이언트 상태는 조정에 필요한 만큼만 둔다는 것이다.

## 내 사례 세 건

raccoon-territory는 걸음수와 체크리스트로 도토리를 모으는 너구리 육성 앱이다. Next 16
static export를 Capacitor로 감싸고, 클라이언트가 Supabase를 직접 호출한다. 클라이언트
상태는 zustand로 들고 있다.

### 1. 늦게 온 만보기 동기화가 수기 입력을 덮었다

증상: 걸음수를 직접 입력했는데, 잠시 뒤 만보기 동기화가 끝나면서 입력값이 바뀌었다.

원인: 만보기 동기화는 DB에서 오늘 걸음수를 읽고, 그 위에 증가분을 더해 저장한다. 읽기가
진행 중일 때 수기 입력이 끝나도, 동기화는 수기 입력 전의 값을 기준으로 계산을 이어갔다.
아티클이 말하는 "늦은 응답이 최신 상태를 덮는" 상황이다.

수정(`a64f6a8`, 2026-03-08): `useRef` 버전 카운터를 두고, 동기화 시작 시점의 버전을 캡처한다.
수기 입력이 끝나면 버전을 올리고, 응답이 왔을 때 버전이 다르면 결과를 버린다.

```ts
const myVersion = syncCancelVersion.current;
supabase
  .from("daily_steps")
  .select("steps")
  // ...
  .then(({ data }) => {
    if (syncCancelVersion.current !== myVersion) return; // 수기입력으로 인해 무효화된 sync
```

수기 입력 쪽(`handleStepsAdded`)은 `syncCancelVersion.current++`만 한 줄 추가했다.

### 2. 도토리 증가가 읽고-더하고-쓰기라 서로를 덮었다

증상: 보상이 짧은 간격으로 여러 번 들어오면 DB의 도토리가 기대보다 적게 남을 수 있었다.
또 너구리를 탭할 때 `total_acorns`(누적 획득량)가 현재 보유량 기준으로 덮였다.

원인: `addAcornsToProfile`은 프로필을 읽고, `+ amount`를 해서, 다시 `update`했다.
요청 두 개가 같은 값을 읽으면 나중에 쓴 쪽만 남는다. 전형적인 lost update다.
`clickRaccoon`은 더 직접적이었다. 클라이언트가 들고 있던 `currentAcorns`로 다음 값을 계산해
`acorns`와 `total_acorns` 둘 다에 넣었다. 큐에 넣기 전에 다음 상태를 계산하면 덮인다는
아티클의 지적과 같은 구조다.

```ts
// 수정 전 clickRaccoon
.update({
  acorns: currentAcorns + amount,
  total_acorns: currentAcorns + amount,
})
```

수정(`f7d4968`, 2026-10-07): 계산을 DB로 옮겼다. plpgsql 함수 `increment_profile_acorns`가
`acorns = acorns + delta`로 원자적으로 더한다. 호출자는 `auth.uid()` 본인만 허용하고,
`delta`는 양수만 받는다.

```sql
if (select auth.uid()) is null or (select auth.uid()) <> target_user_id then
  raise exception 'not allowed';
end if;
-- ...
set
  acorns = coalesce(public.profiles.acorns, 0) + delta,
  total_acorns = coalesce(public.profiles.total_acorns, 0) + delta,
```

클라이언트의 `addAcornsToProfile`은 `supabase.rpc("increment_profile_acorns", ...)` 호출 하나가
됐고, `clickRaccoon`도 이 함수를 부르도록 바꿨다. 같은 커밋에서 걸음수, 체크리스트 보상
콜백이 `await addAcornsToProfile(...)`로 끝까지 기다리게 했다.

아티클의 "이전 결과 위에 쌓기"를 `useActionState`가 아니라 DB 한 줄로 한 셈이다.
클라이언트가 다음 값을 계산하지 않고 증가분만 보내면, 순서와 상관없이 결과가 쌓인다.

### 3. 로드할 때마다 기본 문구가 사용자 수정을 덮었다

증상: 기본 퀘스트 이름을 고쳐도, 앱을 다시 열면 원래 문구로 돌아갔다.

원인: 기본 퀘스트 문구를 다듬으면서(`f545c62`, 2026-10-07 22:27), 기존 사용자에게도 새 문구를
반영하려고 `ensureDefaultChecklistItems`에 동기화 코드를 넣었다. 로드할 때마다 `source_key`로
내장 기본값을 찾고, `label`이 다르면 기본 문구로 `update`했다. 사용자가 직접 바꾼 이름도
"다르다"에 걸렸다. 서버에 저장된 사용자의 쓰기를, 클라이언트 코드에 박힌 값이 매번 덮은 것이다.

수정(`58a7807`, 2026-10-08 09:02): 동기화 블록을 통째로 지웠다. 기존 항목이 있으면 그대로 돌려준다.

```ts
if (existing.length > 0) return existing;
```

같은 커밋에서 `ChecklistItemEditModal`의 중복 저장도 막았다. `saving` 상태 대신
`savingRef`로 진입을 막아, 같은 렌더 안에서 두 번 눌려도 저장이 한 번만 나가게 했다.

## 세 건을 한 표로

|           | 덮은 쪽                 | 덮인 쪽          | 왜 생겼나                          | 고친 방식                        |
| --------- | ----------------------- | ---------------- | ---------------------------------- | -------------------------------- |
| 걸음수    | 늦게 끝난 만보기 동기화 | 수기 입력        | 시작 시점 값으로 계산을 이어감     | 버전 카운터로 늦은 응답 버림     |
| 도토리    | 나중에 쓴 증가 요청     | 먼저 쓴 증가     | 클라이언트가 다음 값을 계산해 씀   | DB 원자 증가 RPC로 이동          |
| 기본 문구 | 로드 시 동기화 코드     | 사용자 수정 이름 | 코드의 기본값을 서버 값보다 우선함 | 동기화 제거, 서버 값 그대로 사용 |

아티클과 연결하면 이렇다. "큐 전에 다음 상태를 계산하면 덮인다"는 2번의 read-modify-write다.
"마지막 저장 결과 위에 쌓기"는 2번의 `acorns + delta`다. "늦은 응답"은 1번의 버전 카운터가 막았다.

## 다른 점과 한계

이 앱은 서버 액션을 쓰지 않는다. static export라 서버 액션이 없고, 클라이언트가 Supabase를
직접 호출한다. 그래서 Next.js가 액션을 순서대로 처리해 주는 보장도 없다. 요청은 병렬로 나가고
도착 순서도 정해져 있지 않다. 아티클의 `useActionState` 해법을 그대로 쓸 수는 없었고,
순서를 맞추는 대신 순서가 상관없게 만드는 쪽(원자 증가, 늦은 응답 버리기)을 택했다.

롤백도 아티클만큼 정리되어 있지 않다. 도토리는 화면에서 먼저 더하고 RPC는 실패 시 로그만
남긴다. 실패하면 화면과 DB가 어긋난 채로 남고, 다음 프로필 로드에서 DB 값으로 맞춰진다.

그리고 아직 같은 패턴이 남은 경로가 있다. 도토리 선물(`giftAcornsToProfile`)은 여전히 읽고-더하고-쓰기
구조다. 이 경로도 원자 RPC로 옮길 계획이다.

## 배운 점

- 클라이언트가 "다음 값"을 계산해서 보내면 순서에 기대게 된다. 증가분만 보내고 계산은 저장하는 쪽에 맡기면 순서가 상관없어진다.
- 늦게 올 수 있는 응답은 시작할 때 버전을 캡처하고, 도착했을 때 비교한다. 취소가 안 되는 요청도 결과는 버릴 수 있다.
- 코드에 박힌 기본값으로 서버 값을 "보정"하는 로직은 사용자의 쓰기와 경합한다. 기본값은 생성할 때 한 번만 쓴다.
