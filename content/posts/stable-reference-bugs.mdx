> 관련 프로젝트: [Moneytermi](/projects/moneytermi)
> 읽은 글: [참조 안정성을 타입으로 만들기](https://www.yeongseo-blog.site/blog/referential-stability-types) ([원문](https://www.jovidecroock.com/blog/referential-stability-types/) Jovi De Croock)

Moneytermi의 커밋 기록에는 의존성 배열을 고친 커밋이 여러 개 있다. 셋은 배열에 무언가를 빠뜨린
것이고, 하나는 같은 라우트에 다시 들어올 때 컴포넌트가 새로 마운트되지 않아 생긴 문제다. 이 글을
읽고 "참조 안정성이 타입에 있었다면 이 중 몇 개가 컴파일 단계에서 걸렸을까"를 판정해 봤다.

## 아티클 요약: 안정성은 렌더 사이의 계약이다

저자는 `unique symbol`로 만든 브랜드 타입 `Stable<T>`를 제안한다. 어떤 값이 렌더가 바뀌어도 같은
참조로 유지된다는 사실을 타입에 붙여, 의존성 배열이나 메모이즈된 자식 props에 불안정한 값이
들어가면 타입 검사에서 걸리게 하는 방식이다.

여기서 안정성은 불변성과 다르다. 값의 내용이 바뀌지 않는다는 뜻이 아니라, 렌더 사이에 같은 참조를
돌려준다는 약속이다. 그래서 `useState`의 setter나 `useRef`가 돌려주는 객체는 기본으로 `Stable`이다.

구현 쪽에서 눈에 띄는 대목은 모듈 보강이 통하지 않았다는 이야기다. React의 기존 타입을 보강해
엄격한 시그니처를 얹으면, 조건에 안 맞는 호출이 에러를 내는 대신 원래 있던 느슨한 오버로드로 조용히
넘어간다. 그래서 별도의 엄격한 진입점(`stableref/react`)에서 훅을 다시 내보내는 쪽을 택했다.

저자는 이 방식이 React Compiler를 대체하는 게 아니라 보완한다고 본다. 컴파일러가 자동으로 메모이즈하는
범위 밖의 계약을 타입으로 남길 수 있고, 코드를 고치는 에이전트에게도 넘지 말아야 할 선이 된다. 한계도
분명히 적는다. 타입 단언 한 번이면 브랜드를 붙일 수 있으니, 결국 지키는 사람이 지켜야 하는 약속이다.

## 내 사례 네 건

Moneytermi는 React + Vite로 만든 토스 미니앱이다. 아래 네 건은 모두 커밋으로 남아 있고, 코드는
`git show`로 확인한 실제 diff다.

### 1. `useMemo`에 `knownWords`가 빠졌다 (`a343fce`, 04-08)

퀴즈 선택지를 만드는 `useMemo`가 `knownWords`를 쓰면서 배열에는 넣지 않았다. 아는 단어가 바뀌어도
선택지가 다시 계산되지 않는다.

```ts
const options = useMemo(() => {
  if (!currentWord) return [];
  return getOptions(currentWord, knownWords, allWords);
}, [currentWord?.id, allWords, knownWords]); // knownWords 추가
```

### 2. effect가 `ready`를 기다리지 않았다 (`f70b093`, 04-08)

진도 데이터를 불러오면 아는 단어 id를 ref(`pendingKnownIds`)에 잠시 담아 두고, 단어 목록(`allWords`)이
오면 effect에서 실제 단어로 바꾼다. 이 effect의 배열이 `[allWords]`뿐이었다. 커밋 메시지는 이걸
"로드 레이스 컨디션"이라고 적었다.

코드로 보면 단어 목록이 먼저 도착한 경우, 그 뒤에 ref가 채워져도 effect가 다시 돌지 않는다. ref를
바꾸는 건 렌더를 일으키지 않기 때문이다. 수정은 배열에 `ready`를 넣어 로드가 끝나는 시점에 한 번 더
돌게 한 것이다.

```ts
}, [allWords, ready]);
```

### 3. ref로 만든 "초기화 완료" 플래그 (`63e0982`, 03-26)

더 이른 시점의 같은 종류 버그다. 동기화 effect들이 `initialized.current`가 `true`일 때만 서버에
쓰도록 막혀 있었다. 그런데 초기 로드가 끝나 ref가 `true`가 돼도 effect는 다시 실행되지 않는다. 그
사이에 바뀐 값은 다음 변경이 올 때까지 서버에 반영되지 않았다.

```diff
-  const initialized = useRef(false);
+  const [ready, setReady]                 = useState(false);
...
-    if (!initialized.current) return;
+    if (!ready) return;
```

ref를 state로 바꾸고, `points`, `knownWords`, `unknownWords`, `missions`를 동기화하는 effect 배열마다
`ready`를 넣었다. 2번도 같은 종류다. ref를 채우는 것만으로는 effect가 다시 돌지 않는다.

### 4. 같은 라우트로 다시 들어오면 이전 index가 남았다 (`a829d2a`, 09-25)

단어 카드에서 관련 용어를 누르면 같은 `/word-card` 라우트로 새 단어 목록을 들고 다시 이동한다.
라우트가 같으니 컴포넌트는 재마운트되지 않고, 현재 단어 index state가 이전 값에 머문다. 원래는
`location.state`가 바뀔 때 index를 다시 맞추는 effect로 막고 있었는데, 커밋 메시지 기준으로 범위 밖
index 크래시와 가짜 완료가 남아 있었다.

수정은 effect를 지우고 라우트 element에 `key`를 준 것이다.

```tsx
<Route path="/word-card" element={<WordCardScreen key={location.key} />} />
```

이동할 때마다 `location.key`가 바뀌니 컴포넌트가 새로 마운트되고, state가 처음부터 시작한다.

## `Stable<T>`가 있었다면

아래 판정은 아티클의 설계를 내 코드에 대입해 본 **추정**이다. 실제로 `Stable<T>`나 `stableref`를
도입해 돌려 본 적은 없다.

| 버그                  | 원인 유형                         | 잡았을까(추정) | 근거                                                                                                                                                  |
| --------------------- | --------------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. `knownWords` 누락  | 배열에 넣을 값을 빠뜨림           | 못 잡음        | 브랜드는 배열에 들어간 값의 안정성을 본다. 빠진 값은 검사 대상이 아니다                                                                               |
| 2. `ready` 누락       | 배열에 넣을 값을 빠뜨림           | 못 잡음        | 1번과 같다. 빠진 것이 state라 오히려 `Stable` 여부와 무관하다                                                                                         |
| 3. ref 플래그         | 렌더를 안 일으키는 값을 신호로 씀 | 못 잡음        | `useRef` 객체는 기본으로 `Stable`이라 타입상 문제없는 값이다. 문제는 `.current`를 읽는 방식이다                                                       |
| 4. 같은 라우트 재진입 | 재마운트 여부, state 초기화       | 부분적         | 이전 effect는 `location.state`가 매번 새 참조라는 점에 기대 있었다. 불안정한 값이 배열에 있다고 표시는 됐겠지만, 고친 방법(`key`)까지 이끌지는 못한다 |

정리하면 네 건 중 셋은 "배열에 무엇이 빠졌나" 또는 "무엇이 렌더를 일으키나"의 문제였다. 아티클이
겨냥하는 "불안정한 값이 배열에 들어가 매 렌더 다시 실행된다"는 유형은 내 커밋 기록에서 찾지 못했다.

## 다른 점과 한계

나는 참조 안정성을 타입으로 강제하는 시도를 하지 않았다. 대신 `react-hooks/exhaustive-deps` 린트에
기대 왔고, 그 린트를 끈 줄이 있다. 2026-10-07 커밋(`933e1a1`) 기준 `src`에서
`eslint-disable` 주석으로 `react-hooks/exhaustive-deps`를 끈 곳은 7곳이고, 파일 7개에 한 곳씩 있다.
누락을 잡는 도구를 일부러 끈 자리라서, 1, 2번 같은 버그가 다시 생긴다면 이 7곳이 먼저 의심할 곳이다.

`Stable<T>`는 이 7곳을 검증해 주지 못한다(추정). 의도적으로 뺀 의존성이 맞는지는 타입이 아니라
주석과 사람이 판단해야 한다. 타입 단언으로 우회할 수 있다는 아티클의 한계도 같은 이야기다. 결국 둘 다
"지키기로 한 약속"을 어디에 적어 두느냐의 차이다.

React Compiler도 도입하지 않았다. 1번처럼 메모이즈 배열을 손으로 쓰다 생긴 누락은 컴파일러가 대신
계산했다면 생기지 않았을 수도 있지만, 이것도 확인하지 않은 추정이다.

## 배운 점

- 의존성 배열 버그는 안정성보다 누락이 더 많았다. 타입보다 먼저 `exhaustive-deps`를 끈 자리부터 센다.
- effect를 다시 돌리고 싶은 신호는 ref가 아니라 state로 둔다. ref는 바뀌어도 아무도 모른다.
- 같은 라우트 재진입에서 state를 맞추는 effect보다 `key`로 새로 마운트하는 쪽이 짧고 확실했다.
