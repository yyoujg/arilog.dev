JavaScript Weekly에서 이 글을 봤다. 기계 검사를 쌓으라는 글인데, 읽으면서 떠오른 건 검사가 틀린 신호를
준 날이었다. 사내 디자인 시스템 스토리북에 접근성 CI 잡을 붙인 날, Scrollbar 키보드 테스트가 CI에서만
실패했다. 나는 테스트를 세 번 고쳤고, 원인은 테스트에 없었다.

## 아티클 요약: 사람이 볼 양을 기계가 줄인다

코드가 만들어지는 속도가 사람이 리뷰하는 속도를 넘으면, 리뷰를 더 열심히 하는 걸로는 따라잡을 수 없다.
그래서 기계가 먼저 걸러 사람이 볼 양을 줄이자는 글이다. 열 가지를 든다.

1. OpenAPI에서 타입을 생성하고 런타임 경계는 Zod로 검증한다.
2. TypeScript strict에 `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`까지 켠다.
3. 린트 플러그인을 쓴다.
4. 레이어 경계를 린트로 강제한다.
5. 실제로 난 사고를 커스텀 규칙으로 만든다. 원인 사고를 댈 수 없는 규칙은 만들지 않는다. 반올림을 두 번
   해서 26시간 15분이 26시간 18분이 된 사고가 예로 나온다.
6. 규칙 파일과 skill을 두고, 바뀐 파일만 린트하는 hook을 건다.
7. Stryker로 mutation testing을 한다. 약 4,700개 변이를 증분으로 돌려 약 6분이 걸린다고 한다.
8. Knip으로 죽은 코드를 찾는다.
9. jscpd로 중복을 찾는다.
10. CI에서 각 검사를 별도 잡으로 두고 배포를 그 결과에 건다.

결론은 초록불이 누군가 코드를 이해했다는 뜻은 아니라는 것이다.

## 내 사례: 2026-08-07 하루

### 오전: 접근성 잡을 붙였다

11시 32분 `bcbcfcc`에서 `test-storybook` 잡을 새로 만들었다. 스토리북의 컴포넌트 테스트를 돌리고,
addon-a11y의 axe 결과를 JSON 리포트로 남기는 잡이다. 접근성은 report-only로 시작했다. 스토리북 설정의
`parameters.a11y.test`를 `"todo"`로 두면 위반이 있어도 테스트는 실패하지 않고, 요약 스크립트가 로그에
위반 수를 찍는다.

첫 버전에는 구멍이 있었다. 요약 스크립트를 `after_script`에서 `npm run a11y:summary || true`로 불렀고,
스크립트는 리포트 파일이 없으면 경고만 찍고 `exit(0)`했다. 테스트가 하나도 안 돌아도 잡이 초록일 수 있는
구조였다. 12분 뒤 `b2e9cef`에서 Playwright 브라우저 설치를 더하면서 이걸 고쳤다. `|| true`를 빼고,
리포트가 없거나 검사한 스토리가 0개면 `exit(1)`한다.

```js
if (!existsSync(reportPath)) {
  console.error(`[a11y] ERROR: report not found: ${reportPath}`);
  process.exit(1);
}
```

### 오후: Scrollbar 테스트가 CI에서만 실패했다

13시 34분에 접근성 회귀 확인 스토리를 더했고, 오후에는 Scrollbar의 `KeyboardArrowScroll` 테스트가 CI에서
실패했다. 언제부터 실패했는지는 파이프라인 기록을 다시 보지 않아 확인하지 않았다. 뷰포트에 포커스를 주고 ArrowDown을 누르면 `scrollTop`이 늘어나는지 보는 테스트다.
로컬에서는 통과했다.

여기서 나는 테스트가 틀렸다고 가정했다. 그리고 세 번 고쳤다.

| 시각  | 커밋      | 고친 것                                                               | 가정                       |
| ----- | --------- | --------------------------------------------------------------------- | -------------------------- |
| 14:05 | `ba71893` | `fireEvent.keyDown`을 `userEvent.keyboard`로, 단정을 `waitFor`로 감쌈 | 이벤트가 가짜라 안 먹는다  |
| 14:20 | `175b3bd` | 시작 전에 `scrollTop = 0`으로 되돌림                                  | 이미 스크롤된 상태다       |
| 14:29 | `fff735e` | `focus()`를 `focus({ preventScroll: true })`로                        | 포커스가 스크롤을 움직인다 |

`ba71893`에는 사실 답에 가까운 단정이 들어 있었다.

```ts
await waitFor(() => {
  expect(viewport.scrollHeight).toBeGreaterThan(viewport.clientHeight);
});
```

뷰포트가 넘칠 만큼 내용이 있는지를 먼저 확인하는 줄이다. 넘치지 않으면 키를 아무리 정확하게 눌러도
스크롤은 안 된다. 그런데 나는 이 줄을 전제 조건으로 넣었을 뿐, 이게 실패하고 있다는 쪽으로 의심을
옮기지 않았다.

세 번째 수정도 실패하자 14시 36분 `d6a9026`에서 값을 찍는 로그를, 14시 53분 `194f851`에서 진단용 코드를
넣었다. 뷰포트의 계산된 높이와 `overflowY`, 스타일시트에 `.h-hg-80` 규칙이 있는지를 문자열로 모아
일부러 실패하는 단정에 넣었다. CI 로그에 그 문자열이 찍히게 하려는 것이었다.

### 원인: CI에는 CSS 파일이 없었다

15시 1분 `e081aae`의 커밋 본문에 원인을 적었다. 스토리북 프리뷰가 참조하는
`public/design-system/v091/styles.css`는 `.gitignore` 대상이라 커밋된 적이 없고, `npm run sync:ds-css`로만
생성된다. CI의 새 체크아웃에는 이 파일이 없었다. 프리뷰의 CSS 요청이 404가 되면서 `h-hg-80`,
`overflow-y-auto`를 포함한 유틸리티가 전부 빠졌고, Scrollbar 뷰포트는 높이 제한이 없으니 넘칠 일이
없었다.

`package.json`을 보면 왜 로컬에서는 통과했는지도 보인다.

```json
"prestorybook": "npm run sync:ds-css",
"prebuild-storybook": "npm run sync:ds-css",
...
"test-storybook": "vitest --project storybook run",
```

스토리북을 띄우거나 빌드하면 CSS가 생성되지만, `test-storybook`에는 그런 훅이 없다. 로컬에서는 스토리북을
한 번이라도 띄웠으니 파일이 남아 있었을 것이다. 이건 코드에서 읽은 추정이다.

고친 건 CI 스텝 한 줄이었다.

```yaml
- npm run sync:ds-css
```

8초 뒤 `5739f1c`에서 디버그 코드 51줄을 원복했다. 앞의 세 수정은 원복하지 않았다. 지금 Scrollbar 스토리에도
`userEvent`, `scrollTop = 0`, `preventScroll`이 그대로 있다.

## 다른 점과 한계

아티클의 다섯 번째 항목, 실제 사고를 규칙으로 만들라는 말에 비추면 이 사고는 규칙이 되지 않았다.
`e081aae`가 더한 건 CI 스텝이다. `test-storybook` 스크립트 자체에는 지금(2026-10-07 기준)도 CSS를 만드는
훅이 없다. 새로 받은 레포에서 스토리북을 띄우지 않고 테스트부터 돌리면 같은 일이 생길 수 있다. 이후 CI가
다른 빌드 환경으로 옮겨질 때 빌드 스펙에도 `npm run sync:ds-css`가 테스트 앞에 명시돼 있지만, 그것도 스텝을
옮겨 적은 것이지 "CSS가 없으면 테스트가 먼저 실패한다"는 검사는 아니다. 프리뷰 CSS가 404면 바로 실패하는
단정 하나가 아티클이 말하는 규칙에 가까웠을 것이다.

접근성 점수를 진단용으로 시작한 건 아티클의 권고와 같다. 다만 승격은 아직 없다. 스토리북 설정의
`a11y.test`는 지금도 `"todo"`다. 요약 스크립트는 리포트가 없거나 스토리가 0개면 실패하지만, 위반이 몇 개든
실패하지는 않는다. 어느 규칙부터 에러로 올릴지 정한 기록은 없다.

AI가 쓴 코드를 거르자는 글이지만 내 사례에서 틀린 가정을 세 번 반복한 건 리뷰 속도 문제가 아니었다.
같은 가정 위에서 수정만 바꿨다. 처음부터 194f851처럼 환경을 찍어 봤다면 한 번에 끝났을 것이다.

## 배운 점

- CI에서만 실패하면 테스트를 고치기 전에 환경 차이부터 찍는다. 계산된 스타일, 로드된 스타일시트, 파일 존재 여부.
- 전제 조건 단정이 실패하면 그게 답이다. `scrollHeight > clientHeight`가 깨졌다는 건 키보드가 아니라 레이아웃 문제라는 뜻이었다.
- 사고에서 CI 스텝만 남기면 그 스텝이 없는 다음 환경에서 같은 사고가 난다. 스텝과 함께 "없으면 바로 실패하는" 검사를 남긴다.
