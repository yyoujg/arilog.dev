같은 글로 개인 프로젝트의 덮어쓰기 버그를 정리한 관련 글이 있다([앞선 쓰기가 조용히 사라졌다](/blog/posts/optimistic-update-lost-write)). 이번에는 회사 코드다. B2B 어드민 요금 화면에서 고친 버그 하나인데, 원인이 된 줄도
고친 줄도 내가 썼다. 그 사이가 16개월이다.

## 아티클 요약: 확정된 결과와 진행 중인 의도는 다른 상태다

글은 사용자가 여러 번 연달아 조작할 때 쓰기를 어떻게 조정하는지 다룬다. 핵심은 다음 상태를 언제
계산하느냐다. 요청을 큐에 넣기 전에 다음 상태를 미리 계산해 두면, 앞선 변경이 반영되기 전 값을
기준으로 계산하게 되어 앞 변경이 덮인다.

저자는 `useActionState`가 이 문제를 구조로 푼다고 설명한다. 이전 액션의 결과가 다음 액션의 입력으로
넘어오기 때문에, 각 변경이 마지막으로 확정된 결과 위에 쌓인다. 실패하면 이전 상태를 그대로 돌려주는
것으로 롤백이 끝난다.

그 바탕에 깔린 원칙은 데이터의 주인이 서버라는 것이다. 클라이언트 상태는 조정에 필요한 만큼만 둔다.
확정된 결과(서버)와 아직 진행 중인 사용자의 의도를 섞지 않고, 각자 어디에 있는지 분명히 한다.

## 내 사례: 동기화 결과가 다음 선택보다 우선했다

### 화면 구조

상품 폼에 "요금 동기화" 버튼이 있다. 누르면 그 상품의 시설, 객실, 패키지 식별자를 jotai atom에
담고 요금 탭으로 이동한다.

```tsx
const handleSyncPayment = () => {
  setPayAsync({
    roomId: String(curRoomId),
    pkgId: String(selectPkgId),
    hotelId: String(activeHotelId),
  });
  setSelectTab("요금");
  // 요금 화면으로 이동
};
```

요금 화면의 검색 영역은 react-hook-form 폼이고, 시설, 객실, 패키지 셀렉트가 각자 목록 쿼리를 가진다.
객실 목록은 선택된 시설과 패키지로, 패키지 목록은 선택된 시설과 객실로 조회한다. 동기화로 들어왔을
때 이 셀렉트들이 atom 값으로 미리 채워져 있어야 했다.

현재 코드 기준으로 이 atom을 쓰는 곳은 상품 폼 한 곳(`setPayAsync` 호출 한 줄)뿐이고, 비우는 코드는
없다. 한 번 동기화하면 새로고침하기 전까지 atom에 값이 남는다.

### 원인이 된 한 줄 (`09e93d90`, 2025-04-01)

"요금동기화버튼 버그픽스"라는 커밋에서 객실, 패키지 셀렉트의 쿼리 입력을 이렇게 바꿨다.

```tsx
const watchedHotelId = watch("hotelId");
const watchedPkgId = watch("pkgId");

const hotelId = payAsync?.hotelId || watchedHotelId;
const pkgId = payAsync?.pkgId || watchedPkgId;
```

왜 이렇게 했는지는 커밋에 기록이 없다. 코드로 보면 동기화로 들어온 직후 폼 값이 채워지기 전에도 목록
쿼리가 atom 값으로 바로 돌게 하려던 것으로 보인다(추정).

문제는 `||`의 의미다. atom 값이 있으면 폼 값은 보지 않는다. 그리고 atom은 비워지지 않는다. 그래서
동기화를 한 번 한 뒤에는 사용자가 시설 셀렉트를 바꿔도 객실, 패키지 목록 쿼리의 입력이 그대로였다.
셀렉트에 보이는 값은 바뀌는데 아래 목록은 이전 시설의 것이 남는다.

### 되돌린 커밋 (`4e14283c`, 2026-08-03)

커밋 메시지는 "요금 동기화 후 payAsync 값이 사용자 선택을 덮어써 목록 미갱신되는 문제 수정"이다.
수정은 두 파일에서 `||` 앞쪽을 지운 것이다.

```diff
-  const hotelId = payAsync?.hotelId || watchedHotelId;
-  const pkgId = payAsync?.pkgId || watchedPkgId;
+  const hotelId = watchedHotelId;
+  const pkgId = watchedPkgId;
```

이제 목록 쿼리는 폼 값만 본다. atom은 effect에서 `setValue`로 폼에 값을 채우는 데만 쓰인다. 동기화
결과는 폼의 초기값 역할로 물러나고, 그 뒤의 선택은 폼이 들고 있다.

다만 "한 번 채우고 끝"이라고 단정하기는 어렵다. 객실, 패키지 셀렉트의 두 번째 effect는 목록 데이터가
바뀔 때마다 다시 돌고, atom의 식별자가 새 목록에 있으면 다시 `setValue`를 한다. atom이 비워지지 않으니
같은 시설 안에서 다른 선택을 바꿔 목록이 다시 오면 동기화 값으로 되돌아갈 수 있는 경로가 코드상 남아
있다. 이 경로로 재현한 기록은 없다. 이 수정은 커밋 당일(2026-08-03) 병합 `a91f31e8`로 dev에,
`cefb1619`로 main에 들어갔다.

## 아티클과 나란히 놓으면

|                      | 아티클                              | 내 사례                                             |
| -------------------- | ----------------------------------- | --------------------------------------------------- |
| 확정된 결과          | 서버가 돌려준 마지막 액션 결과      | 요금 동기화 시점에 atom에 담은 식별자               |
| 진행 중인 의도       | 사용자가 막 누른 다음 변경          | 동기화 뒤 사용자가 셀렉트에서 고른 값               |
| 둘의 관계            | 의도가 확정 결과 위에 쌓인다        | `\|\|` 때문에 확정 결과가 의도를 가렸다             |
| 우선순위가 정해진 곳 | `useActionState`의 이전 상태 인자   | 셀렉트 컴포넌트 안의 한 줄, 문서나 주석 없음        |
| 끝나는 시점          | 액션이 끝나면 결과가 새 기준이 된다 | atom을 비우지 않아 동기화 값이 계속 살아 있었다     |
| 고친 방향            | 이전 결과를 다음 입력으로 넘긴다    | 쿼리 입력을 폼 하나로, atom은 폼을 채우는 데만 쓴다 |

아티클이 경고하는 것은 앞선 확정 결과가 다음 변경에 덮이는 쪽이다. 내 경우는 방향이 반대다. 오래된
확정 결과가 사용자의 다음 선택을 덮었다. 그래도 뿌리는 같다. 둘 중 무엇이 기준인지를 구조로 정하지
않고, 한 줄의 연산자로 암묵적으로 정했다.

## 다른 점과 한계

아티클은 서버 액션과 `useActionState` 이야기다. 내 화면에는 서버 액션이 없다. jotai atom과
react-hook-form 폼, 그리고 TanStack Query 목록 쿼리가 있을 뿐이다. 그래서 "이전 결과를 다음 입력으로"
같은 구조를 그대로 가져올 수는 없었다. 내가 할 수 있었던 건 쿼리 입력의 원천을 폼 하나로 줄이는
것까지였다.

또 "서버가 데이터를 소유한다"는 원칙과도 조금 비껴 있다. atom에 담긴 건 서버 응답이 아니라 동기화
버튼을 누른 순간의 화면 값이다. 굳이 나누면 "이전 화면에서 확정된 값"이다. 그 값이 다음 화면의 기본값
역할만 해야 했는데, 기본값이 아니라 우선값이 됐다.

남은 문제도 적어 둔다. atom을 비우는 시점은 아직 정하지 않았다. 위에서 적은 effect 재실행 경로도
고치지 않았다. 둘 다 "동기화 값의 수명이 어디까지인가"라는 같은 질문이다.

## 배운 점

- `a || b`로 두 원천을 합치면 우선순위 규칙을 만든 것이다. 그 규칙은 a가 비워지는 시점까지 함께 정해야 끝난다.
- 다른 화면에서 넘겨받은 값은 폼의 초기값으로만 쓰고, 그 뒤의 기준은 폼 하나로 둔다.
- 16개월 전 내가 쓴 줄도 커밋 메시지에 이유가 없으면 남의 코드와 다르지 않았다. 우선순위를 정하는 줄에는 이유를 남긴다.
