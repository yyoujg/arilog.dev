이 글은 버그 수정 기록이 아니다. 아티클을 기준으로 너구리 게임의 현재 코드를 다시 읽고,
상태가 어디에 있고 충돌이 어떻게 정리되는지 진단한 기록이다. 고친 것은 앞 글에서 다룬
원자 증가 하나뿐이고, 나머지는 아직 계획이다.

## 아티클 요약: 알림 전파와 상태 관리는 다르다

저자는 Redux, Zustand, Jotai 같은 이른바 상태 관리 라이브러리가 실제로 하는 일은 "값이
바뀌었다"는 알림을 구독자에게 퍼뜨리는 것이라고 본다. 표현력으로 따지면 Pub/Sub와 다르지 않다.

저자가 말하는 진짜 상태 관리는 시간, 순서, 충돌 해결이다. 여러 곳에서 같은 값을 바꿀 때
무엇이 먼저였는지, 둘이 부딪히면 무엇이 이기는지를 정하는 일이다. 이 분야에는 벡터 클록,
CRDT, OT 같은 오래된 답이 있다.

작은 컴포넌트 안의 상태는 상태 머신 정도면 충분하다. 문제는 앱 전체의 충돌을 같은 도구로
풀려는 데서 생긴다. 저자는 이 영역에 Y.js, Zero, Fluid 같은 도구를 권한다.

## 내 코드에서 본 것

raccoon-territory는 Next 16 static export를 Capacitor로 감싼 앱이다. 클라이언트가 Supabase를
직접 호출하고, 상태는 zustand에 둔다. 서버 상태 캐시(SWR, TanStack Query 같은 것)는 쓰지 않는다.

### 1. 도토리와 레벨이 localStorage와 DB 두 곳에 있다

`src/store/useAcornStore.ts`는 `persist` 미들웨어로 스토어를 localStorage에 저장한다.
`partialize`로 고른 값에 서버 값인 `acorns`, `level`이 들어 있다.

```ts
{
  name: "acorn-store",
  partialize: (s) => ({ acorns: s.acorns, level: s.level, lastActiveAt: s.lastActiveAt }),
}
```

앱을 열면 먼저 localStorage 값으로 화면이 그려진다. 로그인 후 `SignalProvider`가 프로필을
불러와 `setFromProfile`로 덮어쓴다. 같은 값의 원천이 둘이고, 정리 규칙은 "나중에 쓴 쪽이
이긴다"다. 이 규칙은 어디에도 적혀 있지 않고, 호출 순서로만 존재한다.

### 2. 레벨업은 "큰 값이 이긴다"로 정리한다

시간이 지나면 자동으로 쌓이는 도토리는 `addAcorns`로 클라이언트 스토어에만 더해진다.
이 값은 레벨업 때 DB로 간다. `src/utils/profile.ts`의 `levelUpProfile`은 클라이언트 값이
DB 값보다 크면 클라이언트 값을 DB에 쓴다.

```ts
if (currentAcorns > dbAcorns) {
  const { error: syncError } = await supabase
    .from("profiles")
    .update({ acorns: currentAcorns })
    .eq("id", userId);
  if (!syncError) dbAcorns = currentAcorns;
}
```

여기서 충돌 규칙은 "큰 값이 이긴다"다. 다른 기기에서 도토리를 쓴 뒤라면 DB 값이 더 작고,
이 기기의 오래된 큰 값이 그 위를 덮는다(코드 구조로 본 추정이고, 재현해 본 것은 아니다).

### 3. 부재 보상은 클라이언트 시계로 계산한다

`syncOfflineAcorns`는 localStorage에 저장된 `lastActiveAt`과 현재 `Date.now()`의 차이로
보상을 계산한다. 시간의 기준이 서버가 아니라 기기 시계다. 아티클이 말하는 "시간"을
클라이언트가 혼자 정하고 있는 셈이다. 계산된 보상은 수령할 때 `addAcornsToProfile`로
DB에 더해진다.

### 4. 친구와 파트너 데이터는 폴링으로 맞춘다

친구, 파트너 프로필은 `useAuthStore`에 들어 있고, `SignalProvider`가 focus,
visibilitychange 이벤트와 5초 간격 폴링으로 다시 불러온다. 친구 목록 폴링 간격은 원래
15초였고, `f7d4968`(2026-10-07)에서 5초로 줄였다. 파트너 프로필 폴링도 같은 커밋에서 5초로
추가했다. 이 값은 내가 바꿀 수 없는 남의 데이터라 서버가 권위이고, 클라이언트는 읽어서
보여주기만 한다. 아티클 기준으로 보면 이 경로는 충돌이 없고, 신선도만 문제다.

## 어떤 값을 누가 정하나

| 값                     | 저장 위치             | 지금 권위를 가진 쪽 | 충돌 규칙                     |
| ---------------------- | --------------------- | ------------------- | ----------------------------- |
| 도토리 증가(보상, 탭)  | DB                    | 서버                | `acorns + delta` 원자 증가    |
| 도토리, 레벨 (로드 시) | localStorage, DB      | 나중에 쓴 쪽        | `setFromProfile`이 덮어씀     |
| 도토리 (레벨업 시)     | 클라이언트 스토어, DB | 큰 쪽               | 클라이언트 값이 크면 DB에 씀  |
| 부재 보상 계산         | localStorage          | 클라이언트          | 기기 시계 기준 `lastActiveAt` |
| 친구, 파트너 프로필    | DB                    | 서버                | 읽기 전용, 5초 폴링           |

표로 놓고 보니 zustand가 한 일은 아티클이 말한 그대로였다. 값이 바뀌면 화면에 알렸다.
충돌을 정리한 건 zustand가 아니라 호출 순서, `>` 비교, 기기 시계 같은 곳에 흩어진 암묵 규칙이었다.

앞 글의 원자 증가 RPC(`increment_profile_acorns`)는 이 규칙 중 하나를 서버로 옮긴 것이다.
"클라이언트가 다음 값을 계산해 쓴다"는 규칙이 "서버가 증가분을 더한다"는 명시적 규칙이 됐다.

## 지금 CRDT를 도입하지 않는 이유

아티클이 권하는 Y.js 같은 도구는 여러 사람이 같은 문서를 동시에 편집하는 문제를 푼다.
이 앱에서 한 사용자의 도토리를 동시에 바꾸는 주체는 그 사용자의 기기 하나, 많아야 두어 개다.
친구 데이터는 읽기만 한다. 협업 편집이 아니고, 충돌 지점도 표에 적은 몇 곳뿐이다.

그래서 지금 판단은 CRDT를 들이기보다, 표의 암묵 규칙을 하나씩 서버의 명시적 규칙으로
옮기는 쪽이 비용 대비 맞다는 것이다. 동시 편집 기능이 생기면 그때 다시 본다.

## 계획

아래는 아직 하지 않았고, 할 계획이다.

- 레벨업을 서버 함수로 옮겨, 비용 차감과 레벨 증가를 DB에서 한 번에 처리한다. "큰 값이 이긴다" 규칙을 없앤다.
- 자동 획득 도토리를 클라이언트에만 쌓지 않고 서버에 반영하는 방식을 정한다.
- `persist`의 `partialize`에서 서버 값(`acorns`, `level`)을 빼고, 로드 전 화면은 로딩 상태로 둘지 검토한다.
- 부재 보상의 시간 기준을 서버 시각(`last_active_at`)으로 옮길지 검토한다.
- 앞 글에서 남겨 둔, 아직 같은 패턴이 남은 경로도 원자 RPC로 옮긴다.

## 배운 점

- 상태 라이브러리를 쓰고 있다는 것과 충돌 규칙이 있다는 것은 별개다. 규칙은 따로 적어야 보인다.
- 값마다 "누가 권위인가"를 표로 적으면, 원천이 둘인 값과 암묵 규칙이 바로 드러난다.
- 충돌 해결 도구를 고르기 전에 충돌 지점이 몇 개인지부터 센다. 적으면 서버 규칙으로 옮기는 게 먼저다.
