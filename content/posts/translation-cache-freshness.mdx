번역을 시트에서 관리하게 만든 이야기는 [앞선 글](/blog/posts/i18n-google-sheets-single-source)에 썼다.
이 글은 그 번역이 브라우저에 도착한 뒤의 이야기다. B2C 리뉴얼에서 이벤트 팝업이 첫 접속에는 안 뜨고
새로고침해야 떴다. 고치는 동안 같은 번역 데이터를 세 군데에서 꺼내 쓰고 있었고, 그중 어느 쪽을
얼마나 오래 믿을지를 한 번 정했다가 뒤집었다.

## 아티클 요약: 로컬을 먼저, 서버는 뒤에서

Linear를 밖에서 분석한 글이다. 빠르다고 느끼는 이유를 두 갈래로 나눈다.

**조작이 빠른 이유.** 변경은 서버보다 로컬에 먼저 반영된다. IndexedDB와 MobX 상태를 먼저 바꾸고, 동기화
엔진이 뒤에서 서버로 보낸다. 다른 사용자의 변경은 WebSocket으로 변경분만 내려온다. 서버가 거부하면
낙관적으로 바꿨던 값을 되돌린다. 반응성은 객체 단위가 아니라 속성 단위라서, 값 하나가 바뀌면 그 값을
쓰는 곳만 다시 그린다.

**첫 화면이 빠른 이유.** 최신 브라우저만 대상으로 빌드하고, 청크를 나누고 `modulepreload`로 미리 받는다.
서비스 워커가 자원을 미리 캐시한다. 테마 같은 설정은 localStorage에서 읽어 첫 페인트 전에 적용한다.
인증 확인은 화면을 그린 뒤 뒤에서 한다.

글의 결론은 기법 하나하나보다 "로컬이 먼저, 낙관적으로"라는 원칙을 초기에 정하고 끝까지 지켰다는 점이다.

## 내 사례: 번역이 팝업 일정이기도 했다

### 구조: 같은 번역이 세 군데에 있었다

번역 데이터는 이렇게 흘렀다.

1. **서버 버전 체크 쿼리.** 언어와 경로를 키로 현재 번역 버전 번호를 받는다.
2. **서버 전체 번역 쿼리.** 버전이 localStorage에 저장된 값과 다르거나, localStorage가 비어 있으면
   언어별 전체 번역을 받아 localStorage에 저장한다.
3. **localStorage.** `languageVersion`과 언어별 번역(`languageKO` 등)을 들고 있다.
4. **i18n 번들.** 빌드에 들어간 기본 JSON이 초기 리소스이고, localStorage 값을 `addResourceBundle`로
   덮어쓴다. 화면이 실제로 읽는 건 여기다.

여기에 한 가지가 더 얽혀 있었다. 이벤트 팝업의 노출 기간과 문구가 번역 키였다.
`EventPopupContainer.tsx`에서 시작일과 종료일을 `eventStartDate`, `eventEndDate` 같은 키로 `t()`에 넘겨
읽는다. 번역이 늦게 도착하면 팝업 일정도 늦게 도착하는 구조였다.

### 1. 문구 판정을 i18n 대신 localStorage로 (2025-12-19)

`78a67309`의 커밋 제목은 "description 캐싱 오류 수정"이다. 본문이 비어 있어서 화면에서 무엇이 보였는지는
기록이 없다. diff로 보면 판정 기준을 옮겼다. 이전에는 `t(key) !== ''`로 문구가 있는지 봤는데, 이걸
localStorage를 직접 읽는 함수로 바꿨다.

```ts
const raw = localStorage.getItem(`language${curLang.toUpperCase()}`);
if (!raw) {
  return false;
}
const languageData = JSON.parse(raw);
const value = languageData[key];
// 키가 존재하고, 값이 있고, 빈 문자열이 아닌 경우만 true
return value !== undefined && value !== null && value !== "";
```

여기에 `fallbackLng: false`와 "번역 결과가 키와 같으면 숨긴다"는 조건을 더했다. i18n 번들이 들고 있는
값보다 localStorage가 더 믿을 만하다고 본 셈이다. 진실의 원천이 둘이라는 걸 이때 처음 코드로 인정했다.

### 2. 키가 그대로 나오면 아직 안 온 것이다 (2026-01-15)

`75f7971b`의 제목이 증상이다. 이벤트 팝업이 새 창이나 첫 접속에는 안 뜨고 새로고침해야 떴다.

이전 코드는 기간 번역이 키와 같으면 "기간 체크 실패"로 보고 팝업을 닫았다. 당시에는 첫 접속에서 번역이
아직 도착하지 않아 `t('eventStartDate')`가 키 문자열을 돌려준다고 보고 고쳤다. 하지만 이 커밋 시점의 기본
JSON(`ko.json`, `en.json`)에는 이미 지난 기간(2025-12-30 ~ 2026-01-05) 값이 들어 있어서, 첫 렌더의 `t()`는
키가 아니라 그 지난 값을 돌려줬을 수 있다. 같은 커밋에서 effect 첫 줄의 `rev === 0` 가드도 지웠다. 그래서
원인은 추정으로 남는다. 낡은 기본 JSON 값으로 기간을 판정했을 가능성과, `rev` 가드가 판정 시점을 바꿨을
가능성이 있고, 어느 쪽이 실제 원인이었는지는 기록이 없다. 새로고침하면 localStorage에 이미 번역이 있으니 떴다.

```ts
// 번역 키가 그대로 반환되면 번역 데이터가 아직 로드되지 않은 것
if (startDateStr === eventData.startDate || endDateStr === eventData.endDate) {
  return;
}
```

코드로는 "값이 없음"과 "아직 안 옴"을 나눴다. 키가 그대로 오면 닫지 않고 기다렸다가, 번역이 들어오면 다시
판단하도록 의존성에 `curLang`을 더했다.

### 3. 5분 동안 믿기로 했다 (2026-01-21)

`1843c090`에서 두 가지를 넣었다. 하나는 버전 체크와 전체 번역 쿼리 양쪽에 `staleTime` 5분, `gcTime` 10분을
준 것이다. 다른 하나는 localStorage에 번역이 있으면 경로가 바뀔 때마다 바로 i18n 번들에 주입하는 이펙트다.

```ts
const raw = localStorage.getItem(`language${cur.toUpperCase()}`);
if (!raw) {
  return;
}

try {
  const parsed = JSON.parse(raw);
  i18n.addResourceBundle(cur, "translation", parsed, true, true);
  i18n.reloadResources([cur], ["translation"]).then(() => {
    setRev((r) => r + 1);
  });
} catch {
  return;
}
```

방향은 아티클과 같다. 로컬에 있는 값을 먼저 화면에 쓰고, 서버는 뒤에서 확인한다. 5분이라는 숫자를
고른 이유는 커밋 본문이 비어 있어 기록이 없다.

### 4. 버전 체크만 0으로 되돌렸다 (2026-02-04)

2주 뒤 `a15c5baa`에서 버전 체크의 `staleTime`만 0으로 바꿨다. 커밋 제목은 "이벤트 팝업 노출 기간 변경 시
새로고침 없이 즉시 반영되도록 수정"이다.

```ts
queryKey: ['checkLanguageVersion', lang, pathFlag],
queryFn: () => getCheckLanguageVersion(lang),
select: data => data.data.data,
staleTime: 0,
gcTime: 1000 * 60 * 10
```

버전 체크 쿼리의 키에는 경로가 들어 있다. `staleTime`이 5분이면 같은 언어, 같은 경로의 키에 대해서는
5분 동안 서버에 다시 묻지 않는다. 그동안 운영 쪽에서 팝업 기간을 바꿔 번역 버전이 올라가도 브라우저는
모른다. 팝업 기간이 번역 키이니, 번역을 5분 믿는다는 건 팝업 일정을 5분 늦게 안다는 뜻이었다.

전체 번역 쿼리의 5분은 그대로 뒀다. 버전이 바뀌면 컨텍스트가 `refetch()`를 직접 부르는데, 이건
`staleTime`과 상관없이 다시 받는다. 언제 다시 받을지는 버전 체크가 정하고, 전체 번역의 `staleTime`은
그 판단에 끼지 않는다.

### 5. localStorage가 비어 있을 때 (2026-02-04)

같은 날 `93957b36`은 시크릿 창을 다뤘다. localStorage가 비어 있으면 3번의 즉시 주입은 할 게 없다.
버전이 바뀌었을 때 localStorage를 i18n에 넣는 이펙트도 전체 번역 응답보다 먼저 돌면 빈 localStorage를 본다.
이 경우를 위해 전체 번역 쿼리가 성공하면 응답을 바로 i18n에 넣는 이펙트를 더했다. 같은 버전을 두 번
넣지 않도록 언어별로 마지막 주입 버전을 `useRef`에 기억한다.

## 다른 점과 한계

아티클의 구조와 가장 크게 다른 점은 서버가 먼저 알려주는 길이 없다는 것이다. Linear는 서버 쪽 변경이
WebSocket으로 내려오니, 로컬을 믿어도 언젠가 맞춰진다는 보장이 있다. 우리는 변경을 알려면 물어봐야 했다.
그래서 "로컬을 얼마나 오래 믿을지"를 시간으로 정해야 했고, 그 시간이 길면 팝업 일정이 늦고 짧으면 요청이
는다. 5분에서 0으로 간 건 그 사이에서 정확성을 고른 결정이다. 0으로 바꾼 뒤 요청이 얼마나 늘었는지는
측정한 기록이 없다.

진실의 원천이 셋인 것도 그대로 남았다. 고친 방식은 원천을 하나로 줄인 게 아니라, 판정할 때 어느 쪽을
볼지(localStorage)와 아직 안 온 상태를 어떻게 알아볼지(키 문자열)를 정한 것이다. 키 문자열로 판별하는
방식은 번역 값이 우연히 키와 같으면 틀린다.

아티클의 "설정을 첫 페인트 전에 적용"과 달리, 우리 주입은 `useEffect` 안에서 돈다. 첫 렌더는 기본 JSON으로
그려지고 그 뒤에 바뀐다. 팝업처럼 판단이 걸린 곳만 기다리게 했을 뿐 화면 전체를 기다리게 하지는 않았다.

## 배운 점

- 같은 데이터를 여러 곳에 두면, 각 원천을 언제까지 믿을지를 데이터별로 표에 적는다. 이번에는 다섯 줄이었고, 커밋 다섯 개에 흩어져 있었다.
- 번역 같은 "정적인" 데이터에도 일정이 실려 있을 수 있다. 무엇이 실려 있는지가 `staleTime`을 정한다.
- "값이 없음"과 "아직 안 옴"은 다른 조건으로 판단한다. 이번 원인은 확정하지 못했지만, 둘을 섞은 판정은 캐시가 비어 있는 첫 접속에서 결과가 달라질 수 있다. 새로고침으로 재현되지 않는 버그는 이 지점을 먼저 본다.
