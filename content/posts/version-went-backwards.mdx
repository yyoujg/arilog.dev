> 관련 프로젝트: [사내 디자인 시스템](/projects/design-system)
> 관련 글: [배포했는데 출시가 아니었다](/blog/posts/shipping-is-not-deploying)
> 읽은 글: [[번역] 빅테크에서 프로젝트를 출시하는 방법](https://imnotadevleoper.tistory.com/394) ([원문](https://www.seangoedecke.com/how-to-ship/) Sean Goedecke, 유승완 번역)

이 글은 1인 미니앱의 출시 대장을 돌아보는 데 한 번 썼다. 회사 쪽에도 같은 질문을 던져 볼 일이
있었다. 사내 디자인 시스템(`@h2o/design-system`)은 패키지를 레지스트리에 올리면 소비 앱(예약 SaaS,
운영 백오피스)이 의존성을 올려 받아 간다. 여기서 "출시됐다"는 건 무엇을 기준으로 말해야 하는지,
버전이 거꾸로 적혔던 이틀을 놓고 다시 봤다.

## 아티클 요약: 출시는 기본값이 아니다

저자의 출발점은 큰 조직에서 프로젝트는 그냥 두면 출시되지 않는다는 것이다. 기본값은 지연이다.
출시를 자기 일로 여기고 끝까지 미는 사람이 있어야 나간다.

또 하나는 출시가 사회적인 판정이라는 점이다. 코드가 운영에 나갔어도 위에서 출시로 인정하지
않으면 출시가 아니다. 그래서 출시 담당자는 "지금 당장 출시할 수 있는가"를 계속 묻고, 막판에
터질 문제를 미리 대비하고, 가능하면 일찍 내보내고, 안 될 때의 대체 계획을 준비해 둔다.

## 내 사례: 0.5.1 다음이 0.4.1이었다

### 증상: 이틀 사이 버전 기록

커밋 기록을 시간순으로 펼치면 이렇다. 모두 내 커밋이다.

| 날짜  | 커밋      | 내용                                                                      |
| ----- | --------- | ------------------------------------------------------------------------- |
| 08-03 | `b4cb5d1` | "버전 번호 오류 수정 0.2.7 -> 0.4.1"                                      |
| 08-04 | `b570d24` | 0.4.1 -> 0.5.0                                                            |
| 08-04 | `0fdeebd` | `index.ts`에서 빠진 Badge, Button, Breadcrumb export 복구, 0.5.0 -> 0.5.1 |
| 08-05 | `211c5ac` | 0.5.1 -> 0.4.1                                                            |
| 08-05 | `e4d8678` | develop을 master로 머지                                                   |
| 08-05 | `e716575` | 0.4.1 -> 0.5.2                                                            |
| 08-05 | `b42cc65` | master 머지 revert                                                        |
| 08-05 | `2809e2b` | 머지 과정에서 유실된 Button border-bw 수정 복원                           |
| 08-05 | `69a0dce` | 함께 유실된 Popover max-width 420px 복원                                  |
| 08-05 | `94ba6da` | 0.6.0 -> 0.6.1, BreadcrumbItem export 복구                                |

`211c5ac`에서 0.5.1 다음 버전을 0.4.1로 적었다. 커밋 메시지는 "0.4.1 버전업"뿐이라 왜 그 숫자를
썼는지는 기록이 없다. 0.4.1은 바로 이틀 전 `b4cb5d1`에서 이미 쓴 번호였다.

### 원인: 이미 있는 버전은 조용히 건너뛴다

배포 파이프라인에는 publish 전에 레지스트리에 같은 버전이 있는지 확인하는 가드가 있었다.
07-16에 내가 `da23aaf`로 넣었고, 같은 날 팀에서도 거의 같은 가드를 담은 커밋(`fa1cea9`)이 따로
올라왔다. 내 단독 작업은 아니다.

```sh
PUBLISH_VERSION=$(node -p "require('./package.json').version")
if npm view "@h2o/design-system@${PUBLISH_VERSION}" version >/dev/null 2>&1; then
  echo "${PUBLISH_VERSION}은 이미 레지스트리에 존재함 - publish 생략(재시도/중복 트리거로 판단)"
  exit 0
fi
npm publish --tag "$DIST_TAG"
```

목적은 같은 태그로 파이프라인을 다시 돌렸을 때 재발행 금지 에러로 job이 실패하지 않게 하는
것이었다. 그런데 이 가드는 "실수로 이미 쓴 번호를 다시 적은 경우"도 똑같이 성공으로 끝낸다.
0.4.1이 master에 들어가 publish 단계까지 갔다면 가드가 `exit 0`으로 넘어가고 파이프라인은 초록이
됐을 것이다. 다만 그 파이프라인이 실제로 skip으로 끝났는지는 확인하지 못했다. 이 부분은 추정이다.

### 수정: revert가 다른 수정까지 지웠다

`e716575`로 develop의 버전을 0.5.2로 바로잡고, master에 들어간 머지는 `b42cc65`로 되돌렸다. revert
사유는 커밋에 따로 적혀 있지 않다.

문제는 그다음이었다. revert 커밋의 diff에는 버전 번호만 있는 게 아니었다. 그 머지가 가져온 Button
outline의 border-bw 수정과 Popover의 max-width 420px도 함께 되돌려져 있었다. 이 revert를 담은 master를
다시 develop으로 합치면서 두 수정이 develop에서도 사라졌고, `2809e2b`와 `69a0dce`로 하나씩 복원했다.
버전 숫자 하나를 고치려던 조치가 실제 수정 두 건을 지운 셈이다.

같은 시기에 `index.ts` export 누락도 두 번 있었다. 08-04에 Badge, Button, Breadcrumb export가 빠진
것을 `0fdeebd`로, 08-05에 BreadcrumbItem이 빠진 것을 `94ba6da`로 복구했다. 컴포넌트 파일은 있는데
진입점에서 내보내지 않으면 빌드도 publish도 성공하고, 소비 앱에서 import할 때야 드러난다.

지금 레포 로컬 작업 규칙(`CLAUDE.md`, git에 올리지 않은 파일)에는 이런 줄이 있다. 파일이 git 밖에 있어
언제 적었는지는 기록이 없다.

> 중복 버전은 실패가 아니라 조용히 skip된다. 파이프라인 초록만 보고 배포됐다고 판단하지 않는다.
> publish 실측으로 확인한다.

참고로 09-22에 팀에서 패키지 CI를 다른 빌드 환경으로 옮기면서, 지금 레포의 CI 설정 파일에서는 이
`npm view` 가드를 찾을 수 없다. 새 환경에서 같은 버전을 어떻게 처리하는지는 이 글에서 확인하지 않았다.

### 소비 앱이 받는 버전으로 다시 계산한 일

9월 말에는 반대 방향의 판단이 있었다. DatePicker 계열 export 세 개를 하나로 합치는 설계 문서에서,
처음 계획은 기존 export를 한 마이너 버전 동안 얇은 wrapper로 남기고 다음 마이너에서 지우는 것이었다.
예약 앱이 패키지를 쓰고 있고 0.x라는 이유였다.

스토리북 레포의 `e3d7986`(09-28)에서 이 계획을 고쳤다. 근거는 두 가지 실측이었다.

- 소비 앱 두 곳을 `git grep`해 보니 DatePicker 계열 사용처가 0건이었다.
- 0.x에서 캐럿은 마이너를 고정한다. 예약 앱은 `^0.17.0`이라 `<0.18.0`, 백오피스는 `^0.16.0`이라 `<0.17.0`이다. breaking을 0.18.0으로 내면 두 앱 모두 자동으로 받지 않는다.

그래서 wrapper 없이 제거하기로 정정했다. 레지스트리에 0.18.0이 올라가는 것과 소비 앱이 그 코드를
받는 것은 별개의 사건이다.

## 대비

|                  | 아티클                        | 내 사례                                                 |
| ---------------- | ----------------------------- | ------------------------------------------------------- |
| 출시의 판정자    | 리더십이 출시로 인정해야 출시 | 소비 앱의 lock 파일에 그 버전이 들어가야 출시           |
| 막판 문제        | 미리 대비해 둔다              | 버전 역행, revert가 지운 수정 두 건, export 누락 두 번  |
| 초록 신호의 함정 | 배포됐다고 출시된 게 아니다   | 가드가 `exit 0`으로 끝나면 publish 없이도 초록 (추정)   |
| 대체 계획        | 안 될 때를 준비한다           | wrapper 유지 계획을 소비처 실측과 캐럿 범위로 다시 계산 |

## 다른 점과 한계

아티클은 여러 팀과 리더십이 얽힌 큰 프로젝트를 다룬다. 내 사례는 패키지 버전 관리라는 훨씬 작은
단위다. "출시를 책임지는 사람"이라는 말을 그대로 가져오기엔 규모가 다르다. 그래도 이틀 동안 버전을
올리고, 머지하고, 되돌리고, 복원한 사람이 모두 나였으니 결과를 확인할 책임도 나에게 있었다.

확인하지 못한 것도 남아 있다. 0.4.1 재발행 시도가 실제로 skip됐는지, 그 사이 소비 앱이 어떤 버전을
받았는지는 기록을 찾지 못했다. 이 글의 원인 서술 중 skip 부분은 가드 코드에서 추론한 것이다.

## 배운 점

- 재시도를 안전하게 하려고 넣은 `exit 0`은 실수도 성공으로 바꾼다. 가드를 넣었다면 "건너뛴 경우"를 따로 확인하는 절차가 같이 있어야 한다.
- 머지를 revert하면 그 머지가 가져온 모든 변경이 되돌려진다. 숫자 하나를 고치려면 revert보다 앞으로 고치는 커밋이 안전하다.
- "출시됐다"는 레지스트리가 아니라 소비 앱 기준으로 말한다. 0.x 캐럿 범위처럼 소비 쪽 조건까지 계산해야 영향 범위가 맞는다.
