이 글은 [레포에 둔 지침도 낡았다](/blog/posts/agent-instructions-in-repo)에서 개인 프로젝트 사례로 한 번
다뤘다. 그때는 혼자 쓰는 레포라 경계도 레포 안에서 끝났다. 회사의 사내 디자인 시스템은 사정이 달랐다.
여러 사람이 커밋하는 팀 레포이고, 만든 결과물을 소비 앱(예약 SaaS, 운영 백오피스)이 받아 쓴다. 그래서
경계를 레포 안과 레포 밖, 두 군데에 그어야 했다.

## 아티클 요약: 공유 시스템 안에서 일하느냐

글은 같은 AI를 써도 직군에 따라 경험이 크게 다르다는 관찰에서 출발한다. 개발자는 AI가 파일, diff,
테스트, 리뷰, 되돌리기 같은 공유 시스템 안에서 일한다. 결과가 기록되고 검토되고 필요하면 되돌려진다.
반면 개인 채팅 창에서만 AI를 쓰면 좋은 지시도 그 대화와 함께 사라진다.

그래서 저자는 지침을 개인 채팅이 아니라 앱 곁에 두라고 한다. 그래야 누군가 지침을 고치면 팀 전체가
그 개선을 받는다. 엔지니어의 역할은 이 시스템의 경계를 정하는 쪽으로 옮겨 간다. 어떤 데이터에 접근할
수 있는지, 어떤 동작에 승인이 필요한지, 무엇은 하지 말아야 하는지를 정한다.

## 내 사례: 경계를 네 겹으로 그었다

### 1. 하지 말 것을 문서로: AGENTS.md

`AGENTS.md`는 07-01에 팀에서 처음 만들었고, 내가 07-15에 `d3fa82c`로 Codex 작업 규칙 형태로 다시 썼다.
핵심은 수정 범위와 추측 금지 두 가지다.

- 지정된 컴포넌트 디렉터리와 진입점 `index.ts`만 수정한다.
- `package.json`, 빌드 설정, `src/design-system/lib/` 하위 공유 프리미티브, 토큰 CSS는 어떤 이유로도 수정하지 않는다. 건드려야 풀릴 것 같으면 수정하지 말고 원인만 보고한다.
- Figma에 명시된 값만 쓴다. 스펙에 없는 border, padding, 색상, 그림자, letter-spacing을 추측해서 넣지 않는다.

아티클이 말한 "무엇은 하지 말아야 하는지"를 파일 경로와 값 출처 단위로 적은 것이다.

### 2. 문서로 부족한 것은 훅으로: husky

문서는 읽히지 않으면 효과가 없다. 07-29 `b95287c`에서 git 훅 세 개를 넣었다.

| 훅         | 하는 일                                                                              |
| ---------- | ------------------------------------------------------------------------------------ |
| pre-commit | `.env*`, `.gitignore` 변경과 tsconfig `moduleResolution` 변경 차단, 변경 파일만 lint |
| commit-msg | `type(티켓키): 설명` 형식이 아니면 차단                                              |
| pre-push   | `npm run typecheck`                                                                  |

`.gitignore`와 `moduleResolution`은 의도된 변경이면 확인 후 `--no-verify`로 넘기라는 안내를 같이 출력한다.
막는 것과 승인을 받고 넘기는 것을 나눈 셈이다.

### 3. 값이 틀리는 사고는 빌드 앞에서: 토큰 검증

토큰은 Figma에서 `tokens.json`으로 사람이 옮긴다. 이 과정에서 생긴 사고들은
[알파값 유실](/blog/posts/design-token-alpha-lost)처럼 전부 사후에 발견됐다. 08-03에 두 개를 넣었다.

- `12789f1`: `scripts/validate-tokens.mjs`. 존재하지 않는 `var(--h2o-*)` 참조, alias 순환, 숫자 접미사 불일치, opacity와 drop-shadow 토큰의 알파 손실을 light와 dark 양쪽에서 검사하고, `build:tokens` 앞단에서 돌린다.
- `ccda259`: `scripts/scan-consumer-impact.mjs`. 기존 토큰의 값이 바뀌었을 때, 그 토큰을 참조하는 소비 앱 파일을 찾아 표로 보여 준다.

순서에 사연이 있다. 검증 단계를 `build:tokens`에 연결하는 변경이 스크립트가 완성되기 전에 버전업
커밋과 함께 develop에 먼저 들어갔다. `429cde5`로 그 연결을 되돌렸고, 그다음 `12789f1`에서 스크립트와
연결을 한 커밋으로 다시 넣었다. 가드레일을 넣는 작업도 미완성 상태로 새면 그 자체가 빌드를 막는
위험이 된다.

영향 스캔은 CI에 넣지 못했다. 스크립트 주석과 README에 이유를 적어 뒀다. 소비 앱 레포가 CI 컨테이너에
체크아웃돼 있지 않으니 로컬 개발자 도구로만 쓴다.

### 4. 레포 밖의 경계: 소비 앱 쪽 검사

디자인 시스템 레포에서 아무리 막아도, 소비 앱이 없는 변수를 참조하면 화면에서만 드러난다. CSS 변수가
없으면 에러 없이 그 속성이 빠질 뿐이다. 그래서 07-23 백오피스 레포에 `28bf1fb`로
`scripts/check-tokens.sh`를 넣었다.

```sh
STYLES="node_modules/@h2o/design-system/dist/styles.css"
[ -f "$STYLES" ] || { echo "SKIP: @h2o/design-system 미설치"; exit 0; }

vars=$(grep -rhoE '\-\-h2o-[a-z0-9-]+' \
  --include='*.ts' --include='*.tsx' --include='*.css' \
  components app 2>/dev/null | sort -u)

[ -n "$vars" ] || exit 0

missing=0
for var in $vars; do
  grep -qE "^[[:space:]]*${var}[[:space:]]*:" "$STYLES" || { echo "MISS: $var"; missing=1; }
done
exit $missing
```

소비 앱 소스가 참조하는 `--h2o-*` 변수를 모아, 설치된 디자인 시스템 `dist/styles.css`에 실제로 정의돼
있는지 대조한다. 하나라도 없으면 `MISS`를 찍고 `exit 1`이다.

### 추측이 남긴 흔적: Logo

08-06에는 Logo 컴포넌트를 같은 날 두 번 커밋했다. 처음 구현(`5649b63`)은 커밋 메시지 기준으로 PNG를
보고 path를 추측해 그린 것이었고, `5548d6f`에서 벡터 원본 기반 path로 교체하면서 그 구현을 폐기했다.
`viewBox`는 `0 0 85 40`에서 `0 0 255.243 141.047`로, 기본 높이는 40에서 47로 바뀌었다. 추측으로 만든
값은 비율부터 틀려 있었다. `AGENTS.md`의 "Figma에 명시된 값만" 규칙이 왜 필요한지를 보여 주는 사례지만,
이 추측이 어떤 경위로 들어갔는지는 커밋에 적혀 있지 않다.

## 다른 점과 한계

아티클은 AI 도구를 중심에 놓지만, 여기 적은 장치 대부분은 사람에게도 똑같이 걸린다. 훅과 검증 스크립트는
커밋한 주체가 누구든 같은 기준으로 막는다. 경계를 AI용으로 따로 만들기보다 공유 시스템 자체에 넣은 쪽에
가깝다.

빈틈도 있다. `check-tokens.sh`는 디자인 시스템이 설치돼 있지 않으면 `SKIP`을 찍고 `exit 0`으로 통과한다.
지금은 npm 스크립트 `check:tokens`로만 연결돼 있고, CI나 훅에서 부르는 곳은 찾지 못했다. 사람이 돌려야
동작하는 경계다. 영향 스캔도 로컬 도구라 MR마다 돌았는지는 남지 않는다.

`AGENTS.md`의 범위 규칙도 모든 작업에 맞지는 않는다. `lib/` 하위는 수정 금지로 적혀 있지만, 07-29에 넣은
포커스 트랩과 Escape 스택은 `lib/`에 새 파일을 만든 작업이었다. 규칙은 컴포넌트 단위 작업의 경계이고,
공유 프리미티브 변경은 별도 티켓으로 진행했다. 이 구분이 문서에 명시돼 있지는 않다.

## 배운 점

- 금지는 문서로 정하고, 꼭 막아야 하는 것은 훅으로 옮긴다. 승인 후 넘길 수 있는 것과 아예 막을 것을 나눠 둔다.
- 디자인 시스템의 경계는 레포 안에서 끝나지 않는다. 소비 앱 쪽에서 "받은 것이 실제로 있는가"를 검사하는 장치가 따로 필요하다.
- `exit 0`으로 끝나는 SKIP 분기는 통과처럼 보인다. 검사가 실제로 돌았는지를 확인할 방법을 같이 둔다.
