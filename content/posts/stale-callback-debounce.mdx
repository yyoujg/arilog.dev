> 관련 프로젝트: [멀티테넌트 예약 SaaS](/projects/multitenant-booking-saas)
> 읽은 글: [참조 안정성을 타입으로 만들기](https://www.yeongseo-blog.site/blog/referential-stability-types) ([원문](https://www.jovidecroock.com/blog/referential-stability-types/) Jovi De Croock)

같은 글로 개인 프로젝트의 훅 버그 네 건을 [의존성 배열이 조용히 틀렸다](/blog/posts/stable-reference-bugs)에서
판정한 적이 있다. 그때 결론은 내 버그 대부분이 안정성이 아니라 누락의 문제였고, 아티클이 겨냥하는
"불안정한 참조" 유형은 기록에서 찾지 못했다는 것이었다. 회사 코드를 보니 그 유형이 있었다. 하나는
B2B 어드민의 예약 검색 필터, 하나는 멀티테넌트 예약 SaaS의 옵션 행이다.

## 아티클 요약: 안정성은 렌더 사이의 계약이다

요약은 앞 글에 자세히 적었으니 이번 글에 필요한 부분만 옮긴다.

- 저자는 `unique symbol` 브랜드로 `Stable<T>`를 만들어, 렌더가 바뀌어도 같은 참조라는 사실을 타입에 붙인다.
- 안정성은 불변성이 아니다. 내용이 아니라 참조가 렌더 사이에 유지된다는 약속이다. 그래서 `useState`의 디스패처와 `useRef` 객체는 기본으로 `Stable`이다.
- React 타입을 모듈 보강으로 엄격하게 바꾸면, 조건에 안 맞는 호출이 에러 없이 기존 느슨한 오버로드로 넘어가 효과가 없다. 그래서 `stableref/react`라는 별도 진입점에서 훅을 다시 내보낸다.
- React Compiler를 대체하지 않고 보완한다. 타입 단언 한 번이면 우회할 수 있다는 한계도 저자가 직접 적는다.

## 사례 1: 예약 검색 필터의 중복 호출 (B2B 어드민)

### 증상과 원인 (`ddbb8f12`, 2025-03-21)

커밋 메시지는 "객실검색 중복호출 제거"다. 예약 검색 필터 컴포넌트에서 조회가 겹쳐 나가던 것을 두
군데 고쳤다.

첫째, 검색 제출이 두 번 조회를 일으켰다. 제출 함수는 검색 조건 atom을 `setCondition`으로 바꾸는데,
예약 목록 쿼리는 이 조건을 쿼리 키에 넣고 있다.

```ts
useQuery<ReservationListResponse>(['rsvList', { ...condition }, page, size, sortBy, isAsc], ...)
```

조건이 바뀌면 키가 바뀌어 자동으로 다시 조회한다. 그런데 제출 함수 끝에서
`queryClient.invalidateQueries(['rsvList'])`를 또 호출하고 있었다. 이 줄을 지웠다.

둘째, 기간 버튼(6개월, 어제, 오늘)을 누르면 제출 effect가 연쇄로 돌았다. 기간 타입 state가 제출
effect의 의존성 배열에 있었고, 동시에 기간 타입을 바꾸는 effect가 `setValue`로 시작일과 종료일을
바꿨다. 이 두 날짜는 `useWatch`로 지켜보는 값이라 제출 effect가 한 번 더 돈다.

```diff
   useEffect(() => {
     debouncedOnSubmit(getValues());
-  }, [watchedValues, curSendType, curDateType]);
+  }, [watchedValues, curSendType]);
```

기간 타입을 배열에서 빼도 날짜 변경을 통해 제출은 한 번 일어난다.

### 디바운스는 왜 이걸 못 막았나

제출 effect는 디바운스된 함수를 부른다. 500ms 안에 두 번 불렸으니 하나로 합쳐졌어야 할 것 같은데,
그 함수는 이렇게 만들어진다.

```tsx
const debouncedOnSubmit = debounce(onSubmit, 500);
```

컴포넌트 본문에 있으니 렌더마다 새 인스턴스가 생긴다. 디바운스의 타이머는 인스턴스마다 따로라,
서로 다른 렌더에서 부른 두 번은 합쳐지지 않는다. 두 번째 원인의 연쇄는 정확히 이 경우다. 기간 타입이
바뀐 렌더에서 한 번, 날짜가 바뀐 다음 렌더에서 한 번 불린다. 당시 중복 호출이 이 경로로 몇 번
나갔는지 잰 기록은 없다. 위 설명은 코드를 읽고 맞춘 추정이다.

`ddbb8f12`는 의존성을 줄여 부르는 횟수를 줄였을 뿐, 디바운스 자체는 건드리지 않았다. 현재 코드에서도
같은 줄이 그대로 있다. 디바운스가 렌더를 넘어 유지되지 않는다는 문제는 아직 고치지 않았다. 같은
저장소에서 `= debounce(` 형태로 만드는 줄은 36곳이고, `useMemo`나 `useRef`로 감싼 곳은 grep 기준
0곳이다. 36곳이 모두 렌더 본문 안인지는 하나씩 확인하지 않았다.

## 사례 2: 옵션 행 memo와 주석으로만 남은 계약 (멀티테넌트 예약 SaaS)

### 무엇을 바꿨나 (`44dcfbd`, 2026-06-15)

레저 상품 상세의 옵션 목록은 원래 부모 컴포넌트의 `map` 안에 전부 들어 있었고, 수량 스테퍼의
`onChange`도 그 자리의 인라인 화살표 함수였다.

```tsx
onChange={(next) =>
  setOptionQty((prev) => ({
    ...prev,
    [opt.id]: next,
  }))
}
```

수량 하나를 바꾸면 옵션 그리드 전체가 다시 그려지는 구조였다. 커밋에서 한 행을 `LeisureOptionRow`로
분리해 `memo`로 감싸고, 수량 변경 콜백을 훅에서 `useCallback`으로 만들어 내려보냈다.

```ts
const onQtyChange = useCallback((optId: string, next: number) => {
  setOptionQty((prev) => ({ ...prev, [optId]: next }));
}, []);
```

나머지 props도 확인했다. 옵션 객체는 `useMemo`로 만든 목록(선택 상품과 상품 데이터가 바뀔 때만 다시
계산)에서 오고, 수량은 숫자, 라벨 두 개는 문자열이다. 코드상으로는 수량이 바뀐 행만 props가 달라진다.
다만 렌더 횟수를 실제로 잰 기록은 없다. 커밋 메시지의 "해당 행만 리렌더"는 의도이지 측정값이 아니다.

### 계약이 적힌 곳

분리한 컴포넌트 위에 이런 주석을 달았다.

```tsx
/**
 * (`onQtyChange` 는 부모에서 useCallback 으로 안정화되어야 memo 가 실효를 가짐)
 */
```

`memo`가 효과를 내려면 props 참조가 안정해야 한다. 이 조건을 나는 주석으로만 적었다. 누군가 부모에서
`onQtyChange`를 인라인 함수로 바꿔도 타입 검사도 린트도 아무 말을 하지 않는다. 화면도 똑같이
동작한다. 리렌더가 늘어날 뿐이라 아무도 모른다. 아티클의 `Stable<T>`가 타입으로 옮기려는 게 정확히 이
주석이다.

## `Stable<T>`가 있었다면

아래는 아티클의 설계를 두 사례에 대입한 **추정**이다. 두 저장소 모두 `Stable<T>`나 `stableref`를 도입해
본 적이 없고, React Compiler 설정도 없다.

| 문제                        | 원인 유형                          | 잡았을까(추정) | 근거                                                                                                                         |
| --------------------------- | ---------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 1-1. 쿼리 키 + `invalidate` | 같은 조회를 두 경로로 요청         | 못 잡음        | 참조 안정성과 무관하다. 쿼리 키가 이미 재조회를 맡고 있다는 걸 몰랐던 문제다                                                 |
| 1-2. 기간 타입 의존성 연쇄  | 같은 변화가 신호 두 개로 들어옴    | 못 잡음        | 배열에 든 값은 모두 state라 타입상 문제가 없다. 신호가 중복된 건 설계 문제다                                                 |
| 1-3. 렌더마다 새 `debounce` | 참조가 유지돼야 의미 있는 인스턴스 | 조건부         | 디바운스 함수를 배열에 넣지 않고 effect 안에서 부르기만 해서 검사 대상이 아니다. `Stable`을 요구하는 자리에 넘길 때만 걸린다 |
| 2. 인라인 콜백 + `memo`     | `memo` 자식에 불안정한 props       | 잡음           | 메모이즈된 자식 props에 `Stable`을 요구하는 타입이면 인라인 화살표는 타입 에러다. 지금 주석이 하는 일을 타입 검사가 한다     |

1-3이 가장 아쉽다. 디바운스, 스로틀처럼 내부에 타이머나 상태를 들고 있는 함수는 참조가 유지되는 것
자체가 기능이다. 그런데 이 코드에서는 그 함수가 의존성 배열에도, `memo` props에도 들어가지 않으니
`Stable<T>`가 볼 기회가 없다. 브랜드 타입이 잡는 건 불안정한 값이 안정성을 요구하는 자리로 넘어가는
순간이고, 렌더 본문에서 만들어 그 자리에서 쓰고 버리는 값은 지나간다.

## 다른 점과 한계

앞 글의 개인 프로젝트 사례는 배열에 무엇이 빠졌느냐의 문제였다. 이번 두 사례는 배열이나 props에 들어간
값, 또는 들어가지 않은 값의 참조가 렌더마다 바뀌는 문제다. 같은 아티클이 두 번 다른 쪽을 비춘 셈이다.

사례 1의 원인 두 개(1-1, 1-2)는 결국 안정성 문제가 아니었다. 그 커밋에서 실제로 지운 건 중복된 요청
경로와 중복된 의존성이고, 디바운스는 손대지 않았다. 지금 와서 보면 디바운스를 렌더 밖으로 꺼냈다면
1-2의 연쇄도 하나로 합쳐졌을 수 있다. 확인하지 않은 추정이다.

사례 2는 계약이 지켜지고 있다. 다만 지켜진다는 근거가 주석과 내 기억뿐이다. 렌더 횟수를 재 두지 않았기
때문에, 계약이 깨져도 그걸 알려 줄 숫자가 없다.

## 배운 점

- 디바운스, 스로틀 인스턴스는 참조가 유지되는 것이 기능이다. 렌더 본문에서 만들면 타이머가 렌더마다 새로 시작한다.
- `memo`의 전제 조건을 주석으로 적었다면 그건 타입이나 테스트로 옮길 후보다. 주석은 깨져도 아무 말을 하지 않는다.
- 안정성 타입은 불안정한 값이 안정성을 요구하는 자리로 넘어갈 때만 본다. 그 자리를 거치지 않는 인스턴스는 사람이 찾아야 한다.
