Korean FE Article 뉴스레터로 이 글이 왔다. 큰 정수, `undefined`, `Date`, `NaN`이
`JSON.stringify`를 한 번 거치면서 바뀌거나 사라지는데, 그 과정에서 예외가 하나도
나지 않는다는 이야기다. 읽으면서 Moneytermi에서 고친 버그 세 건이 떠올랐다.
셋 다 응답은 성공이었고, 값만 틀려 있었다.

## 아티클 요약: 유효한 JSON이 의미를 잃는다

글의 요지는 JSON이 고장 난 게 아니라는 것이다. 작게 설계된 교환 포맷을 자바스크립트
상태의 무손실 복사본처럼 다룰 때 문제가 생긴다.

| 경계를 넘는 값        | 결과                             | 에러 |
| --------------------- | -------------------------------- | ---- |
| 2^53을 넘는 정수      | 반올림된 숫자                    | 없음 |
| `undefined` 프로퍼티  | 키가 사라짐                      | 없음 |
| `Date`                | UTC ISO 문자열, 원래 오프셋 소실 | 없음 |
| `NaN`, `Infinity`     | `null`                           | 없음 |
| `Map`, `Set`, `Error` | 빈 객체                          | 없음 |

저자가 제시하는 규칙은 경계를 명시적으로 만드는 것이다. 와이어 형태를 직접 정의하고,
파싱 뒤에 스키마로 검증하고, 예외적인 값에는 문서화된 표현을 붙이고, 직렬화한 쪽이
아니라 **받는 쪽에서 테스트한다.**

## 내 사례 세 건

Moneytermi는 경제·금융 용어를 카드와 퀴즈로 학습하는 토스 미니앱이다. React + Vite
클라이언트가 Supabase(PostgREST)를 직접 호출한다.

### 1. Date가 UTC 문자열이 되면서 하루가 밀렸다

출석, 연속 학습일(streak), 복습 예정일 비교에 날짜 문자열이 필요했다. 처음에는
`d.toISOString().slice(0, 10)`으로 만들었다. 이 코드가 다섯 군데에 퍼져 있었다.

`toISOString()`은 UTC로 내보낸다. 아티클이 짚은 바로 그 동작이다. 한국 시간 00시부터
09시 사이에는 UTC 날짜가 하루 전이라, 그 시간에 출석하면 전날 출석으로 기록됐다.
자동 출석, streak, 복습 경계가 모두 영향을 받았다.

```ts
// 앱 전역 날짜 문자열은 KST(UTC+9) 기준.
// toISOString()은 UTC라 00:00~09:00 KST 구간에서 하루 밀린다.
export const toDateStr = (d: Date = new Date()) =>
  new Date(d.getTime() + 9 * 60 * 60 * 1000).toISOString().slice(0, 10);
```

고친 방식은 아티클의 "예외적인 값에 명시적인 표현 부여하기"와 같다. 날짜 문자열이
어느 시간대 기준인지를 `lib/date.ts` 한 곳에서 정하고, 다섯 군데를 전부 이 함수로 바꿨다.

### 2. 닉네임 갱신이 0행을 바꾸고 성공으로 끝났다

닉네임을 바꾸면 내 화면에서는 바뀌었는데, 다른 사람의 리그 화면에는 옛 닉네임이 남았다.

`profiles` 테이블의 갱신 정책(RLS)은 게스트 토큰 헤더로 본인 행을 찾는다. 그런데 요청을
헤더 없는 기본 클라이언트로 보내고 있었다. 정책에 맞는 행이 없으니 0행이 갱신됐고,
PostgREST는 이걸 에러로 돌려주지 않는다. 클라이언트는 `error`가 없으니 성공으로 처리하고
로컬 상태만 바꿨다.

```ts
const db = guestToken ? getGuestClient(guestToken) : supabase;
const { data: updated, error: updateError } = await db
  .from("profiles")
  .update({ nickname: trimmed })
  .eq("id", profileId)
  .select("id");

if (updateError || !updated?.length)
  return { error: "닉네임 변경에 실패했어요" };
```

헤더를 붙인 클라이언트로 바꾸는 것만으로는 부족하다고 봤다. `.select('id')`로 갱신된 행을
돌려받고 개수까지 확인해야 "에러 없음"이 "반영됨"과 같은 뜻이 된다. 아티클의 "파싱 후
검증하기"에 해당한다. 문법상 정상인 응답이 내가 기대한 의미를 담고 있는지는 따로 확인해야 한다.

### 3. 1213개 중 1000개만 왔다

용어를 213개 추가해 1213개가 된 날, 1001번 이후 단어가 앱에 나오지 않았다. PostgREST는
한 번에 최대 1000행까지만 돌려준다. 잘린 배열도 완전히 유효한 JSON이고 에러도 없다.

```ts
// PostgREST는 한 번에 1000행까지만 돌려준다. 짧은 페이지가 올 때까지 이어 받는다.
export const PAGE = 1000;

export const fetchAll = async <T>(
  page: (from: number) => PromiseLike<{ data: T[] | null }>,
): Promise<{ data: T[] | null }> => {
  const all: T[] = [];
  for (let from = 0; ; from += PAGE) {
    const { data } = await page(from);
    if (!data) return { data: null };
    all.push(...data);
    if (data.length < PAGE) return { data: all };
  }
};
```

이어 받는 함수와 함께 1001행으로 경계를 넘기는 테스트를 넣었다. 요청이 `0`, `1000`
두 번 나가고 1001개를 전부 받는지 확인한다. 배포 후에는 앱 클라이언트로 직접 조회해
단어 1213개, 코스 연결 1213개를 모두 받는 것까지 확인했다. 아티클이 말하는 "받는 쪽에서
테스트하기"를 실제 수신 경로에서 한 셈이다.

## 세 건을 한 표로

|           | 경계              | 무엇이 바뀌었나       | 왜 안 보였나              | 고친 방식                        |
| --------- | ----------------- | --------------------- | ------------------------- | -------------------------------- |
| 날짜 밀림 | `Date` -> 문자열  | KST 날짜가 UTC 날짜로 | 09시 이후에는 결과가 같다 | 시간대 기준을 함수 하나로 고정   |
| 닉네임    | 클라이언트 -> RLS | 0행 갱신              | `error`가 비어 있다       | 갱신 행을 돌려받아 개수 확인     |
| 1000행    | DB -> 클라이언트  | 1000행에서 잘림       | 1000행 이하일 때는 정상   | 페이지로 이어 받기 + 경계 테스트 |

세 건 모두 특정 조건(시간대, 권한 헤더, 행 개수)에서만 드러났다. 평소에는 맞는 값이
나오니 테스트가 통과했고, 에러가 없으니 로그에도 남지 않았다.

## 다른 점도 있다

엄밀히 말하면 JSON 직렬화 규칙 자체가 원인인 건 1번뿐이다. 2번과 3번은 PostgREST의 동작
(0행 갱신을 에러로 보지 않음, 응답 행 상한)이다. 그래도 아티클의 처방은 그대로 적용됐다.
경계 너머가 무엇을 보장하는지 가정하지 말고 계약으로 적고, 받는 쪽에서 확인한다.
JSON이든 API든 "성공했다"는 신호는 형식이 맞다는 뜻이지 의미가 맞다는 뜻이 아니었다.

## 배운 점

- 응답에 `error`가 없다는 건 형식이 맞다는 뜻이다. 반영된 행 수, 받은 개수처럼 의미를 확인하는 값을 따로 받는다.
- `Date`를 문자열로 바꾸는 코드는 시간대 기준을 함수 하나에 모은다. 흩어져 있으면 한 곳만 고치고 끝난다.
- 경계 테스트는 경계 바로 바깥 값으로 쓴다. 1000이 아니라 1001, 09시 이후가 아니라 08시.
