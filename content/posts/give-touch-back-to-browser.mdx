> 읽은 글: [브라우저에서 실행되는 코드인가, 브라우저가 실행하는 코드인가](https://www.yeongseo-blog.site/blog/more-control-equals-less-performance) (번역본) / [원문](https://blog.jim-nielsen.com/2025/more-control-equals-less-performance/) (Jim Nielsen)

이미지 슬라이더에 드래그를 넣었다가 8일 동안 두 번 고쳤다. 두 번 모두 내가 쓴 코드가 브라우저가 이미 하던 일과 부딪힌 문제였다.
이 글을 읽고 그 과정을 다시 봤다.

## 아티클 요약: 제어를 쥘수록 느려지기 쉽다

글의 질문은 제목 그대로다. 내 코드가 브라우저 안에서 돌아가는가, 아니면 브라우저가 내 선언을 받아 대신 실행하는가.
저자는 뒤쪽을 고르라고 한다. 직접 제어하는 코드가 많을수록 브라우저가 최적화할 여지는 줄어든다.

애니메이션을 예로 든다. `setTimeout`으로 프레임을 돌리던 방식에서 `requestAnimationFrame`, JS로 부르는 View Transitions,
CSS만으로 선언하는 View Transitions로 갈수록 내가 쥐는 제어는 줄고 브라우저가 맡는 몫은 커진다.
`scroll-behavior`, Grid와 Flexbox, `dialog`, `details`, `select`, 폼 검증도 같은 선 위에 있다.
직접 만들 수 있지만, 브라우저가 이미 하는 일이라면 선언으로 넘기는 편이 낫다는 이야기다.

## 내 사례: 이미지 슬라이더

### 출발점

슬라이더(`components/common/ImageSlider.tsx`)는 원래 CSS만으로 넘어갔다. 가로 스크롤 컨테이너에
`snap-x snap-mandatory`, `scroll-smooth`, `touch-pan-x`를 걸어 두면 터치 스와이프와 스냅은 브라우저가 처리한다.

### 1. JS 드래그를 넣었다 (ea5af7c, 06-02)

스와이프 지원을 넣으면서 pointer 이벤트로 드래그를 직접 구현했다. `pointerdown`에서 시작점을 잡고
`setPointerCapture`로 포인터를 붙잡은 뒤, `pointermove`마다 `scrollLeft`를 직접 움직였다.
드래그 중에는 스냅을 끄고(`snap-none scroll-auto`), 손을 떼면 이동 거리로 이전/다음 장을 정했다.

```tsx
if (Math.abs(dx) > 5) dragRef.current.moved = true;
el.scrollLeft = st.startScrollLeft - dx;
```

이 코드는 마우스와 터치를 가리지 않았다. 터치에서도 브라우저의 네이티브 스크롤 위에 내 `scrollLeft` 조작이 겹쳤다.

### 2. 모바일 스와이프 중 이미지가 깜빡였다 (f35265d, 06-04)

이틀 뒤 모바일에서 스와이프 중 이미지가 깜빡였다. 커밋에 남긴 원인은 JS 수동 드래그(`scrollLeft` 직접 조작)가
네이티브 가로 pan과 충돌한다는 것이다. 그 이상의 메커니즘은 기록하지 않았다.

수정은 터치와 펜을 브라우저에 돌려주는 것이었다.

```tsx
// 터치/펜은 네이티브 scroll-snap에 맡긴다
if (e.pointerType !== "mouse") return;
if (e.button !== 0) return;
```

같은 커밋에서 실패한 이미지를 걸러내는 `visibleItems`를 `useMemo`로 감쌌다. 이 변경이 깜빡임에 얼마나 기여했는지는 기록이 없다.

### 3. PC에서 이미지를 눌러도 사진 모달이 안 열렸다 (ad592b1, 06-10)

마우스 드래그는 남겼는데, 이번에는 PC에서 이미지를 클릭해도 사진 모달이 열리지 않았다.
`pointerdown`에서 바로 `setPointerCapture`를 걸었기 때문이다. 캡처가 걸리면 클릭이 캡처 대상인 스크롤 컨테이너로
retarget되어, 자식 버튼의 `onClick`(모달 열기)이 실행되지 않았다.

캡처 시점을 "실제로 5px 넘게 움직였을 때"로 늦췄다.

```tsx
if (Math.abs(dx) > 5 && !st.moved) {
  dragRef.current.moved = true;
  el.setPointerCapture(e.pointerId); // 실제 코드는 try/catch로 감쌌다
}
```

클릭은 다시 브라우저의 기본 흐름대로 버튼에 도착하고, 드래그로 판정된 뒤에만 내 코드가 포인터를 쥔다.

## 보조 사례: 반대로 제어를 더 쥔 결정 (58e96c3, 09-16)

운영 백오피스에서는 반대 방향의 결정을 했다. 모달 안에서 `absolute`로 그리던 달력과 옵션 메뉴가
모달 본문의 `overflow-y-auto`에 잘렸다(1280x800에서 판매 시작일 달력이 헤더만 보였다).
케밥 메뉴는 아래로만 열려 마지막 행에서 화면 밖으로 나갔다.

그래서 `AnchoredPopover`를 직접 만들었다. body 포털에 `position: fixed`로 띄우고, 위치를 계산해 DOM style로 놓는다.
아래 공간이 모자라면 위로 뒤집고, 바깥 클릭, 바깥 스크롤, 리사이즈가 오면 닫는다.
좌우는 뒤집지 않고 `left`를 뷰포트 안으로 clamp만 한다. 그 이상의 충돌 계산은 없고, 주석에 필요해지면 라이브러리로 바꾼다고 적어 두었다.

브라우저의 Popover API나 CSS anchor positioning을 검토했는지는 커밋에도 코드에도 검토 기록이 없다.
주석에 남긴 다음 단계도 브라우저 기능이 아니라 라이브러리였다. 한 가지 흥미로운 점은 스크롤 시 위치를 따라가지 않고 닫는 동작을
"네이티브 select와 같음"이라고 적었다는 것이다. 제어는 직접 쥐었지만 동작의 기준은 브라우저 기본 요소에서 빌려 왔다.

## 아티클과 대비

| 입력/기능           | 처음                        | 나중                            | 누가 처리하나         |
| ------------------- | --------------------------- | ------------------------------- | --------------------- |
| 터치/펜 스와이프    | JS가 `scrollLeft` 직접 조작 | `scroll-snap`, `touch-pan-x`    | 브라우저              |
| 마우스 클릭         | `pointerdown`에서 바로 캡처 | 5px 넘게 움직인 뒤에만 캡처     | 브라우저, 드래그만 JS |
| 마우스 드래그       | JS                          | JS                              | 내 코드               |
| 모달 안 팝오버 위치 | `absolute`                  | body 포털 + `fixed` + 직접 계산 | 내 코드               |

슬라이더 쪽은 아티클의 방향과 같다. 내가 쥔 제어를 줄일수록 버그가 사라졌다.
깜빡임은 터치를 돌려주자 없어졌고, 클릭 문제는 캡처를 늦춰 브라우저의 기본 이벤트 흐름을 지나가게 하자 풀렸다.

## 다른 점과 한계

아티클은 성능을 말하지만 내 사례는 성능 측정이 아니라 동작 오류였다. 깜빡임이 프레임 드랍 때문이었는지는 측정한 기록이 없다.
"제어를 쥐면 브라우저의 기본 동작과 부딪힌다"는 쪽이 내 경험에 더 가깝다.

마우스 드래그는 지금도 JS가 처리한다. 마우스로 끌어서 가로로 넘기는 동작은 스크롤 컨테이너의 기본 동작이 아니라서
선언으로 넘길 곳이 없었다. 브라우저에 맡길 수 없는 부분만 남긴 셈이다.

팝오버는 아티클의 기준으로 보면 반대 방향이다. 모달 안의 잘림을 풀 수 있는 브라우저 기능이 있었는지,
당시 대상 브라우저에서 쓸 수 있었는지는 확인하지 않았다. 직접 만든 만큼 좌우 뒤집기가 없다는 한계는 남아 있다.

## 배운 점

- 브라우저가 이미 하는 일(터치 스크롤, 스냅, 클릭 전달) 위에 같은 일을 하는 코드를 얹으면 둘이 부딪힌다. 먼저 "이건 누가 하던 일인가"를 본다.
- 직접 처리할 때도 범위를 좁힌다. 입력 종류(`pointerType`)와 시점(실제로 움직인 뒤)으로 내 코드가 개입하는 구간을 최소로 둔다.
- 직접 만들기로 했다면 브라우저 기능을 검토했는지 기록을 남긴다. 이번 팝오버에는 그 기록이 없어서, 지금 와서 왜 그 선택을 했는지 설명할 수 없다.
