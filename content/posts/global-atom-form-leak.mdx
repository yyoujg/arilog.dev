> 읽은 글: [[번역] 상태 관리의 참담한 현주소](https://imnotadevleoper.tistory.com/389) (유승완 번역) / [원문](https://infrequently.org/2026/07/state-management/) (Alex Russell)

이 글을 읽고 개인 프로젝트의 상태 구조를 진단한 적이 있다([진실의 원천이 둘이었다](/blog/posts/state-has-two-sources)).
이번에는 회사 코드에서 같은 문제를 겪은 사례를 꺼냈다. 법인 고객 CRM의 패키지 등록/수정 폼이다.
2026년 3월 19일부터 23일 사이에 같은 증상 계열을 다섯 번 고쳤다.

## 아티클 요약: 알림 전파는 상태 관리가 아니다

저자는 Redux, Zustand, Recoil 같은 이른바 상태 관리 라이브러리가 실제로 하는 일은 "값이 바뀌었다"는 알림을
구독자에게 퍼뜨리는 것뿐이라고 본다. 표현력으로 따지면 Pub/Sub와 다르지 않다는 것이다.

저자가 말하는 진짜 상태 관리는 그 다음 문제다. 이 값이 언제 만들어졌는지, 어떤 순서로 바뀌었는지,
두 곳에서 동시에 바뀌면 어느 쪽이 이기는지. 라이브러리는 이 질문에 답하지 않는다.
그리고 컴포넌트 하나 안에서 끝나는 작은 상태라면 큰 라이브러리 대신 상태 머신 정도면 충분하다고 결론짓는다.

## 내 사례: 패키지 폼의 다섯 번 수정

### 구조

패키지 폼의 값은 Recoil atom에 들어 있었다. 등록 화면(`PackageCreateContainer`)과 수정 화면(`PackageUpdateContainer`)이
같은 atom(`packageFormAtoms.ts`의 `packageTypeAtom` 등)을 읽고 쓴다.
법인 패키지의 이메일 도메인 선택값은 하위 섹션 컴포넌트가 로컬 상태(`corporateSelectedDomains`)로 들고 있다가
atom의 값에서 복원했다.

atom은 화면이 바뀌어도 살아 있다. 그래서 atom 안의 값만 봐서는 이게 지금 화면의 값인지,
직전에 본 다른 화면의 값인지 구분할 방법이 없었다.

### 1. 상세를 보고 등록에 들어가면 이전 값이 보였다 (c798bae27, 03-19)

상세 페이지를 본 뒤 등록 페이지로 가면 첫 렌더링에 상세 페이지 값이 그대로 나왔다.
커밋 본문에 적은 원인은 "전역 Recoil atom이 상세 페이지 값을 유지한 채 등록 페이지 첫 렌더링에 노출"이다.
초기화가 `useEffect` 안에 있어서 페인트가 먼저 일어났다.

```tsx
-  useEffect(() => {
+  useLayoutEffect(() => {
     initializeFormData();
   }, [initializeFormData]);
```

이 수정은 초기화를 페인트 앞으로 당겼을 뿐이다. 이전 값이 atom에 남아 있다는 사실은 그대로다.

### 2. 등록 화면이 수정 화면의 도메인 선택값을 복원했다 (3fb48a6f4, 03-20)

도메인 복원 effect는 원래 상세에서 받아온 값을 화면에 되살리려고 만든 것이었다.
그런데 등록 화면에서도 같은 effect가 돌면서, atom에 남은 수정 화면의 값을 복원했다.
화면 종류를 `mode` prop으로 내려 보내고 수정 화면에서만 돌게 막았다.

```tsx
   useEffect(() => {
+    if (mode !== 'edit') return;
```

### 3. 패키지를 바꿔 들어가면 이전 패키지의 도메인이 남았다 (f477b77fd, 03-23)

수정 화면끼리 이동해도 같은 문제가 났다. A 패키지를 보다 B 패키지로 가면 A의 도메인이 남았다.
`pkgId`가 바뀔 때 atom의 도메인 필드를 비우는 effect를 넣었다.

```tsx
+  useEffect(() => {
+    setTypeData(prev => ({ ...prev, categoryId: [], corporateId: [] }));
+  }, [pkgId, setTypeData]);
```

### 4. atom을 비워도 로컬 상태가 남았다 (088802169, 03-23)

atom은 비워졌지만 하위 섹션 컴포넌트가 리마운트되지 않아 로컬 상태 `corporateSelectedDomains`가 그대로였다.
섹션에 `key={pkgId ?? 'package-type-create'}`를 줘서 패키지가 바뀌면 컴포넌트를 새로 만들게 했다.

### 5. 비운 값과 새 값의 순서가 어긋났다 (e812af5cd, 03-23)

같은 날 마지막 수정이다. 커밋 본문에는 React 18 batching 때문에 `pkgId`가 바뀔 때
도메인 선택값이 이전 패키지의 stale 데이터로 초기화되는 race라고 적었다.
비우는 effect와 상세 데이터를 채우는 effect가 어떤 순서로 반영되는지에 따라 결과가 달라졌다는 뜻이다.

그래서 atom에 `initRevision` 카운터를 추가했다. 폼을 초기화할 때마다 1씩 올리고,
도메인 복원 effect는 개별 필드 대신 이 카운터가 바뀔 때만 돈다.

```tsx
-  }, [mode, typeData.categoryId, typeData.corporateId, corporateSelectedDomains.length, corporateGroupData]);
+  }, [mode, typeData.initRevision, corporateGroupData]);
```

```tsx
         corporateId: packageDetail.corporateId ?? [],
+        initRevision: (prev.initRevision ?? 0) + 1
```

## 아티클과 대비

다섯 번의 수정을 놓고 보면, 각각이 atom에 없던 정보를 하나씩 다시 붙인 것이었다.

| 수정              | 붙인 정보               | atom이 답하지 못한 질문                 |
| ----------------- | ----------------------- | --------------------------------------- |
| `useLayoutEffect` | 첫 페인트 전 초기화     | 이 화면이 보여지기 전에 비웠는가        |
| `mode` 가드       | 어느 화면의 값인가      | 등록 화면의 값인가, 수정 화면의 값인가  |
| `pkgId` 초기화    | 어느 패키지의 값인가    | 지금 패키지의 값인가                    |
| `key={pkgId}`     | 컴포넌트 수명           | 로컬 상태가 이 패키지와 같이 태어났는가 |
| `initRevision`    | 몇 번째 초기화의 값인가 | 비우기와 채우기 중 어느 쪽이 나중인가   |

아티클의 말로 하면, Recoil은 "값이 바뀌었다"는 알림은 정확히 전파했다.
문제는 그 값이 언제의, 어느 화면의 값인지를 atom이 모른다는 점이었다. 폼 상태를 전역에 둔 순간 시간 개념이 사라졌고,
다섯 번의 수정은 그 시간 개념을 `mode`, `key`, `revision`으로 하나씩 다시 붙인 과정이었다.

## 다른 점과 한계

아티클은 작은 컴포넌트 상태라면 상태 머신이면 된다고 결론짓는다. 내가 간 방향은 상태 머신이 아니었다.
돌아보면 다섯 번 중 효과가 컸던 수정은 `key={pkgId}`처럼 상태를 컴포넌트 수명에 묶는 쪽이었다.
패키지가 바뀌면 컴포넌트가 새로 태어나고, 로컬 상태도 같이 새로 태어난다. 순서를 따질 필요가 없다.

반대로 `initRevision`은 전역에 남긴 채 순서를 직접 관리하는 방법이다. 동작은 하지만 비용이 있다.
복원 effect의 의존성 배열을 의도적으로 줄였기 때문에 `react-hooks/exhaustive-deps` 규칙을 그 줄에서 꺼야 했다.
린트가 지켜주던 것을 사람이 기억해야 하는 구조가 됐다.

폼 값 자체는 지금도 전역 atom에 있다. 이번 수정은 증상이 난 도메인 선택값 주변을 막은 것이고,
같은 atom을 쓰는 다른 섹션에서 같은 계열의 문제가 생길 여지가 있다고 본다(추정, 확인하지 않았다).
폼 상태를 전역에서 꺼내 폼 컴포넌트 수명에 묶는 것이 근본적인 방향이라고 보지만, 아직 하지 않았다.

또 하나, 다섯 번의 수정 각각이 언제 사용자에게 드러났는지, 운영 데이터에 잘못 저장된 건이 있었는지는 기록이 없다.

## 배운 점

- 전역 상태에 값을 넣을 때는 "이 값은 언제, 어느 화면의 값인가"를 같이 넣지 않으면 나중에 하나씩 덧붙이게 된다.
- 화면 하나에서 시작해 화면 하나에서 끝나는 상태는 그 화면 컴포넌트의 수명에 묶는 것이 가장 싸다. `key` 하나가 effect 여러 개보다 낫다.
- 같은 계열 버그를 연달아 고치고 있다면 증상이 아니라 상태가 사는 위치를 의심한다.
