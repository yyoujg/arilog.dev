blogsumnail에서 이미지 포맷을 고를 때 본 숫자는 하나였다. 몇 바이트인가. 이 글은 같은
이미지가 다 받아지기 전에 화면에 무엇이 보이는지를 포맷별로 비교한다. 그 기준으로 내
설정을 다시 보니, 용량을 줄이면서 다른 걸 내려놓았다는 걸 알게 됐다.

## 아티클 요약: 포맷마다 "먼저 보이는 것"이 다르다

저자는 같은 사진을 포맷별로 인코딩하고, 바이트가 조금씩 도착할 때 브라우저가 무엇을
그리는지 비교한다.

- **JPEG**: 프로그레시브 인코딩이 사실상 공짜다. 약 1.2kB만 받아도 렌더가 시작되고,
  전체의 21%인 33kB에서 첫 패스가 끝난다.
- **WebP**: 43kB(28%)가 와야 처음 보인다. Safari는 아예 프로그레시브로 그리지 않는다.
- **AVIF**: 일반적인 AVIF에는 프로그레시브 렌더링이 없다. `--layered` 옵션으로 인코딩하면
  가능하지만 지원하는 건 Chromium뿐이다.

저자는 프로그레시브가 만능이 아니라는 점도 짚는다. 프로그레시브 렌더링이 이미지 크기
관리를 대신해 주지는 않는다. 고해상도 JPEG XL 하나를 보내고 앞부분만 끊어 쓰는 식으로
반응형 이미지를 대체할 수도 없다. 대신 현실적인 제안으로, AVIF 앞에 작은 블러 미리보기를
붙이는 방식을 든다.

## 내 사례: 용량만 보고 고른 설정들

blogsumnail은 네이버 블로그 썸네일·스킨 메이커와 SEO 가이드 블로그를 함께 둔 Next 16
사이트다. 이미지 관련 결정은 세 번 있었다.

### 1. 원본 JPG 압축과 캐시 (2026-03-29, `3646a7f`)

커밋 제목은 "14개 압축(평균 87% 감소)"인데, `git show --stat`으로 보면 실제로 바뀐
바이너리 파일은 JPG 10개다. 10개 합계가 23,092,600바이트에서 2,600,487바이트로 줄었다
(88.7%). 제목의 14개와 diff의 10개가 왜 다른지는 커밋에 남아 있지 않다.

같은 커밋에서 `next.config.ts`에 `/images/:path*` 경로 `Cache-Control: public,
max-age=31536000, immutable`을 걸고, 전역 `app/layout.tsx`에 카페 사진 preload 2개를 넣었다.

### 2. AVIF 우선 서빙 (2026-07-22, `efd1468`)

```ts
images: {
  // 본문 사진이 4032px 원본이라 전송량이 큼. AVIF 우선으로 webp 대비 20~30% 절감
  formats: ['image/avif', 'image/webp'],
},
```

주석의 "20~30% 절감"은 내가 잰 값이 아니다. 출처도 커밋에 남기지 않았다.

### 3. 전역 preload 제거 (2026-10-06, `625e69b`)

전역 레이아웃에 남아 있던 카페 사진 preload 2개를 지웠다. 모든 페이지가 특정 글의 사진을
미리 받고 있었다.

블로그 본문 이미지는 `app/blog/[slug]/page.tsx`의 `SectionImage`가 그린다. `next/image`에
`width` 800, `height` 800, `sizes="(max-width: 672px) 100vw, 672px"`를 주고, `placeholder`는
지정하지 않았다.

## 프로덕션 실측

2026-10-08 09:50 KST에 먼저 배포 반영 상태를 봤다.

```bash
$ curl -sI https://www.blogsumnail.com/ | grep -iE "^age|x-vercel-cache"
age: 57131
x-vercel-cache: HIT
```

측정 대상은 `/blog/naver-blog-thumbnail-size` 글이다. 이 글 HTML에서 `/_next/image` URL을
뽑아(`grep -o | sort -u`) 그중 `/images/screenshots/tool-thumb-default.png`를 골랐다.
2026-10-08 09:51 KST에 같은 URL을 `Accept` 헤더만 바꿔 요청했다.

```bash
curl -s -o /dev/null -w '%{size_download} %{content_type}\n' \
  -H 'Accept: image/avif,image/webp,*/*' \
  'https://www.blogsumnail.com/_next/image?url=%2Fimages%2Fscreenshots%2Ftool-thumb-default.png&w=828&q=75'
```

| 요청 폭  | `Accept: image/avif,...` | `Accept: image/webp,...` | `Accept` 없음  |
| -------- | ------------------------ | ------------------------ | -------------- |
| `w=828`  | 18,991 B (avif)          | 26,592 B (webp)          | 59,571 B (png) |
| `w=1920` | 29,348 B (avif)          | 45,124 B (webp)          | 96,325 B (png) |

원본 PNG는 344,348바이트다. AVIF는 WebP 대비 `w=828`에서 28.6%, `w=1920`에서 35.0%
작았다. 주석의 20~30%와 대략 맞는 범위지만 이미지 한 장, 두 폭에서 잰 값이라 일반화하지는
않는다. 원본이 PNG라 `Accept` 없는 요청은 JPEG가 아니라 PNG로 돌아왔다. 확인한 블로그
페이지들에서는 JPG 원본을 `/_next/image`로 내보내는 경우를 찾지 못했다.

## 아티클 기준으로 다시 본 표

| 포맷 | 아티클의 프로그레시브 동작                     | 내 사이트 (`w=828`)            |
| ---- | ---------------------------------------------- | ------------------------------ |
| JPEG | 약 1.2kB부터 렌더, 33kB(21%)에서 첫 패스       | 이 이미지에는 해당 없음        |
| WebP | 43kB(28%)부터 표시, Safari는 프로그레시브 없음 | 26,592 B, AVIF 미지원 브라우저 |
| AVIF | 일반 AVIF는 없음, `--layered`는 Chromium만     | 18,991 B, AVIF 지원 브라우저   |

용량으로만 보면 AVIF가 가장 작다. 프로그레시브 기준으로 보면 AVIF를 받는 브라우저에서는
다 받기 전까지 아무것도 그려지지 않는다. `formats`를 켠 순간 이 선택을 한 것인데, 그때는
선택이라고 생각하지 않았다.

## 다른 점과 한계

측정하지 않은 게 더 많다. 느린 망에서 이 이미지가 도착하는 동안 화면에 무엇이 보이는지는
재지 않았다. 지금 쓰는 AVIF가 `--layered`인지도 확인하지 않았지만, Next가 런타임에 만드는
기본 인코딩일 테니 아닐 것이라고 추정한다. 아티클의 사진 예시와 달리 내 측정 대상은 도구
스크린샷 PNG라, 포맷 간 차이도 사진과는 다를 수 있다.

반대로 아티클의 경고 하나는 이미 지키고 있었다. 프로그레시브가 크기 관리를 대신하지 못한다는
부분이다. `sizes`와 `w` 단계로 폭에 맞는 파일을 받게 하고 있고, `w=1920`과 `w=828`의 차이가
그 효과다.

지금 판단은 용량 우선이다. 블로그 이미지가 대부분 본문 중간 스크린샷이라, 첫 화면에 보이는
LCP 이미지가 아닌 경우가 많다고 본다(추정, 페이지별로 확인하지 않았다). 남은 선택지는 계획으로만
적어 둔다.

- `SectionImage`에 블러 `placeholder`를 넣어 AVIF 앞에 미리보기를 둔다. 아티클의 제안과 같은 방향이다.
- 느린 망 에뮬레이션으로 AVIF, WebP 요청을 각각 녹화해 실제로 무엇이 먼저 보이는지 비교한다.

## 배운 점

- 이미지 포맷은 용량 하나로 비교되지 않는다. 다 받기 전에 무엇이 보이는지도 포맷이 정한다.
- 커밋 주석의 수치(20~30%)와 커밋 제목의 개수(14개)는 diff와 실측으로 다시 확인한다. 이번에는 하나는 범위 안이었고 하나는 달랐다.
- 측정한 것과 측정하지 않은 것을 나눠 적는다. 바이트는 쟀고, 느린 망의 화면은 재지 않았다.
