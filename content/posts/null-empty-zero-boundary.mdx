같은 글로 개인 프로젝트의 버그 세 건(날짜 밀림, 0행 갱신, 1000행 잘림)을 정리한 관련 글이 있다([에러 없이 틀린 값이 돌아왔다](/blog/posts/silent-boundary-loss)).
이 글에서는 아티클의 한 부분에만 집중한다. "값이 없음"을 어떻게 표현하느냐다.
회사 코드를 훑어보니 나는 같은 "없음"을 생략, `null`, 빈 배열, `0` 네 가지로 말하고 있었고, 받는 쪽은 그걸 매번 다르게 읽었다.

## 아티클 요약: 없음에도 계약이 필요하다

자바스크립트 객체에서 값이 `undefined`인 프로퍼티는 `JSON.stringify`를 거치면 키째 사라진다.
보내는 쪽은 "값이 없다"고 썼는데, 받는 쪽은 "그 필드를 안 보냈다"만 알게 된다.

저자는 그래서 생략과 `null`의 뜻을 API 계약에서 직접 정하라고 한다. 예로 드는 것이 프로필 수정이다.
닉네임을 지우려면 `null`을 보내고, 그대로 두려면 필드를 생략한다. 이렇게 정해 두지 않으면 두 의도가 와이어에서 구분되지 않는다.

또 하나는 파싱과 검증의 구분이다. `JSON.parse`는 문법이 맞는지만 본다. 그 값이 기대한 의미인지는 따로 스키마로 검증해야 한다.
그리고 그 검증과 테스트는 보내는 쪽이 아니라 받는 쪽에서 해야 한다.

## 내 사례

### 1. 빈 배열: 수정할 때마다 지우기를 보냈다 (B2B 어드민)

패키지에는 법인 이메일 도메인 태그 필드(`tagEmailDomain`, `tagEmailDomainGroup`)가 있다.
a4e009b8(2026-03-27)에서 등록과 수정 모두 이 두 필드를 빈 배열로 강제해서 보내게 했다. 왜 강제했는지는 커밋에 이유가 없다.

```tsx
formattedData.tagEmailDomain = [];
formattedData.tagEmailDomainGroup = [];
await editPackageInfoAsync(formattedData);
```

아티클의 닉네임 예시에 대면, 수정 화면은 저장할 때마다 "지워라"를 보낸 셈이다.
서버가 실제로 기존 태그를 빈 배열로 덮어썼는지는 확인하지 않았다. 덮어썼을 것이라는 건 추정이다.

나흘 뒤 6c260b2d(03-31)에서 수정 화면의 강제 빈 배열을 지우고, 상세 조회 응답 타입에 두 필드를 추가했다.
커밋 메시지대로라면 수정 화면의 초기값을 상세 조회 값으로 채우는 쪽으로 바꾼 것이다.
등록 쪽의 빈 배열 강제는 남아 있다. 새로 만드는 패키지라 의도한 것인지는 확인하지 못했다.

### 2. 빈 배열과 생략: 같은 필드를 상황마다 다르게 보냈다 (법인 고객 CRM)

다른 화면에서 같은 이름의 필드를 다룬 기록이다. d3c2d215a(2026-03-19)의 커밋 본문에 따르면,
기업회원 패키지를 등록할 때 그룹만 고르면 `tagEmailDomain: []`이, 개별 도메인만 고르면 `tagEmailDomainGroup: []`이 요청 바디에 실려
서버가 500을 돌려줬다. 그래서 값이 있을 때만 키를 넣도록 바꿨다.

다음 날 3fb48a6f4(03-20)에서는 반대로 일반회원 패키지일 때 두 필드를 빈 배열로 명시해서 보내게 했다.

```tsx
...(isCorporate
  ? {
      ...(categoryId && categoryId.length > 0 ? { tagEmailDomainGroup: categoryId } : {}),
      ...(corporateId && corporateId.length > 0 ? { tagEmailDomain: corporateId } : {})
    }
  : { tagEmailDomainGroup: [], tagEmailDomain: [] }),
```

같은 필드인데 기업회원 쪽에서는 "선택 안 함"을 생략으로, 일반회원 쪽에서는 "태그 없음으로 초기화"를 빈 배열로 표현했다.
이 규칙은 코드 안에만 있고 계약으로 적힌 곳은 없다.

### 3. 0: falsy라서 검증을 통과했다 (법인 고객 CRM)

패키지의 남은 수량(`allocationLimit`) 검증이다. 62f584ae6(2026-02-05) 전에는 이렇게 되어 있었다.

```tsx
if (allocationLimit && allocationLimit < 1) {
```

`0`은 falsy라 앞 조건에서 걸러지고, 1 미만을 막으려던 검증이 `0`만은 통과시켰다. 나는 `0`을 "0개"라는 값으로 썼는데
이 조건은 `0`을 "값 없음"으로 읽었다. `null`과 `undefined`만 명시적으로 걸러내고,
등록에서는 `0`을 막고 수정에서는 기존 값 `0`을 허용하도록 화면 모드로 나눴다.

```tsx
if (mode === 'create' && allocationLimit !== null && allocationLimit !== undefined && allocationLimit < 1) {
```

### 4. null: 타입은 문자열이라고 했다 (운영 백오피스)

c486bb7(2026-09-09). 엑셀 일괄 등록으로 만든 패키지는 판매 시작일과 종료일이 `null`로 내려왔다.
날짜를 점 표기로 바꾸는 `toDotDate`는 `null`을 가정하지 않고 문자열 메서드를 불렀고,
그 패키지가 속한 시설의 객실 목록 화면 전체가 렌더링되지 않았다.

```ts
-  saleStartDate: string;
-  saleEndDate: string;
+  saleStartDate: string | null;
+  saleEndDate: string | null;
```

단건 생성/수정 API는 이 필드가 필수라 항상 값이 있었다. 같은 필드가 생성 경로에 따라 계약이 달랐고,
프론트 타입은 그중 한 경로만 믿고 있었다. 아티클의 "파싱은 문법만 본다"가 정확히 이 지점이다. 응답은 유효한 JSON이었다.

같은 화면에서 며칠 앞서 고친 것도 있다. 5584680(09-04) 전에는 패키지 만료 여부를 화면 표시용 기간 문자열을
정규식으로 되파싱해 클라이언트 시계와 비교했다. 서버 응답에 이미 `saleExpired` 플래그가 있었고, 그걸 쓰도록 바꿨다.
만료 상태의 테스트 데이터를 만들어, 만료된 것과 안 된 것 각각 플래그와 화면 표시가 맞는지 확인했다.

여기도 "없음"이 끼어 있다. 커밋에 적었듯이 단건 조회 응답에는 `saleExpired`가 없다. 단건 재조회는 `updatedAt`만 갱신하고 `saleExpired`는 건드리지 않는 기존 동작을 그대로 뒀다.
행 타입이 `saleExpired?: boolean`이라, 단건 응답만으로 행을 새로 만들면 `undefined`가 되어 "만료 아님"과 구분되지 않는다. 이 응답에서 필드가 없다는 건 "false"가 아니라 "이 응답은 모른다"는 뜻이다.

### 5. data: null: 성공을 실패로 읽었다 (멀티테넌트 예약 SaaS)

e565fd5(2026-06-16). 설정 저장 API는 성공하면 `success: true, data: null`을 돌려준다.
공용 응답 파서는 `data == null`이면 실패로 던지고 있었다. 저장은 됐는데 화면에는 에러가 떴다.

```ts
-  if (!json || !json.success || json.data == null) {
+  if (!json || !json.success) {
```

`success`와 `data`를 따로 보고, 데이터 없는 성공은 호출부가 `allowEmptyData`로 허용할 때만 통과시키게 했다.
기본값을 바꾸지 않고 opt-in으로 둔 이유는 커밋에 적지 않았다. 결과적으로 다른 API는 지금도 `data: null`을 실패로 본다.

## 네 가지 없음

| 표현   | 내가 의도한 뜻                   | 받는 쪽이 읽은 뜻                                               | 사례                                   |
| ------ | -------------------------------- | --------------------------------------------------------------- | -------------------------------------- |
| 생략   | 선택 안 함 / 이 응답은 모름      | 서버 해석은 확인 기록 없음 / `undefined`라 `false`와 구분 안 됨 | CRM 기업회원 태그, 만료 플래그         |
| `[]`   | 태그 없음으로 초기화             | 수정 저장마다 지우기(추정) / 한쪽만 실으면 서버 500             | B2B 어드민 수정, CRM 기업회원          |
| `0`    | 0개라는 값                       | 값 없음(falsy)                                                  | CRM 남은 수량 검증                     |
| `null` | 판매기간 없음 / 데이터 없는 성공 | 문자열이라고 가정, 실패                                         | 백오피스 판매기간, 예약 SaaS 설정 저장 |

같은 "없음"이 화면마다, 필드마다 다른 표현으로 나갔고, 받는 쪽은 자기가 가정한 뜻으로 읽었다.
에러로 드러난 건 서버 500, 렌더 실패, 성공을 실패로 띄운 에러 모달 세 건이고, 나머지는 조용히 틀렸거나 틀렸을 수 있었다.

## 다른 점과 한계

아티클은 보내는 쪽과 받는 쪽이 계약을 같이 정하는 상황을 전제한다. 내 사례에서는 대부분 서버 계약이 이미 정해져 있었고
문서에 "없음"의 뜻이 적혀 있지 않았다. 프론트에서 할 수 있었던 건 응답을 실측해 타입을 실제에 맞추고(`string | null`),
보낼 때의 규칙을 코드에 명시하는 정도였다.

스키마 검증도 넣지 않았다. 다섯 건 모두 타입 정정과 조건문 수정으로 끝냈다. 런타임에 응답 형태를 검증하는 층이 있었다면
판매기간 `null`은 렌더 전에 잡혔을 것이다. 수신 측 테스트도 이번 수정들에는 남기지 않았다.

빈 배열 사례 두 건은 서버가 그 값을 어떻게 처리했는지를 서버 코드로 확인하지 못했다. 덮어쓰기는 추정이고,
500의 원인도 커밋 본문에 적은 관찰까지만 안다.

## 배운 점

- "없음"을 보낼 때는 생략, `null`, 빈 배열 중 무엇이 무슨 뜻인지 필드마다 정해 둔다. 정하지 않으면 화면마다 다르게 보내게 된다.
- 숫자 필드의 존재 검사에 truthy 체크를 쓰지 않는다. `0`이 유효한 값이면 `null`과 `undefined`만 명시적으로 거른다.
- 응답 타입은 문서가 아니라 실제 응답의 모든 생성 경로를 기준으로 쓴다. 필드가 없는 응답이 있다면 그 없음은 `false`가 아니라 "모름"으로 다룬다.
